# ТЗ. Блок 3 — Изоляция данных платформы redevelopment

> Блок 3 из 4: Авторизация (`TZ-auth.md`) → Админка (`TZ-admin.md`) → **Изоляция данных** → Миграция Матрёшки (`TZ-migration.md`).
> Стек: Vite (React) + Supabase (Postgres + RLS + Storage) + Vercel (`api/*`). Прод — Vercel. Разработка: OpenCode + Grok (`grok-build-0.1` / `grok-4.7`).

---

## 1. Что услышал

Анатолий — владелец платформы; первый клиент — ООО «Матрёшка», админка — `основа.redevelopment.pro` (латинский алиас `osnova.redevelopment.pro` тоже подключён и работает).

Запрос — гарантировать на уровне **базы данных**, что клиент видит и меняет только свои данные:
- данные одного клиента недоступны другому — даже при ошибке в интерфейсе или прямом запросе к API/Supabase;
- общая база поставщиков — одна на всех, а пометки и цены клиента видит только он;
- внутренние данные Анатолия (лиды, финмодели, метрики сайтов и т.п.) клиентам недоступны.

### 1.1. Что сейчас и почему плохо

| Что есть | Почему плохо |
|---|---|
| Одна общая база Supabase, ~50 таблиц: закупки (`purchase_*`), поставщики (`suppliers`, `supplier_*`, `supply_*`), подрядчики (`work_contractor*`), почта (`mailbox_*`, `outgoing_email_jobs`, `unmatched_incoming_emails`), БЦ/ТЦ, SEO-метрики и др. | Ни в одной таблице нет признака «чей это клиент» |
| RLS включён (~50 политик), но правило по сути одно: «вошёл сотрудник → видит всё» | Закупщик Матрёшки увидел бы все закупки, письма и данные Анатолия |
| `suppliers` — одна таблица, в ней же заметки, оценки надёжности, переписка | Общее (карточка) и личное (пометки, цены клиента) смешаны |
| Storage: бакеты без разделения по клиентам | Вложения заявок и писем одного клиента доступны по ссылке всем сотрудникам |
| `api/*` используют `service_role` и проверяют только наличие сессии | Серверный код обходит RLS — изоляция зависит только от аккуратности кода |

## 2. Ограничения и требования

### 2.1. Процесс
- Прод-ветка — `claude/redevelopment-platform-prototype-oodobu` (далее `oodobu`); изменения схемы и политик мёржатся в `oodobu`.
- Автодеплой Vercel из git выключен: прод выкатывается вручную через Vercel CLI, только после «да» Анатолия. Миграции базы — тоже только после «да».

### 2.2. Нефункциональные требования
- Изоляция работает **даже при ошибке во фронтенде** (скрытый пункт меню не считается защитой).
- Индексы по `client_id` во всех клиентских таблицах — запросы не медленнее текущих более чем на 20 %.
- Новая таблица без `client_id` и политик не проходит аудит (п. 3.7).
- Секреты (`service_role`) — только в env Vercel; в бандле и репозитории их нет.
- Журнал фиксирует все отказы доступа (403) с пользователем, клиентом и таблицей/функцией.
- Сайты (redevelopment.pro, malllist, officelist) и публичные токен-страницы работают как раньше.

### 2.3. Границы блока (что НЕ входит)
- ❌ Вход, пароли, сессии, Битрикс24 — **блок 1** (`TZ-auth.md`).
- ❌ Интерфейс админок, разделы, переключатель — **блок 2** (`TZ-admin.md`).
- ❌ Перенос существующих данных и проставление `client_id` историческим записям — **блок 4**. В блоке 3: схема, политики, тесты; существующие данные помечаются клиентом «redevelopment» (внутренний), без разбора.
- ❌ Физическое разделение (отдельная база/схема/проект Supabase на клиента).
- ❌ Шифрование отдельных полей, хранение данных в РФ, бэкапы по клиентам.
- ❌ Биллинг и квоты по клиентам.

## 3. Что будет сделано и как проверю

### 3.1. Целевое состояние

```
Supabase (одна база, схема public)
│
├── ОБЩЕЕ (платформа)          suppliers, supply_categories, supplier_contacts …
│     читают все вошедшие; правит только platform_owner
│
├── КЛИЕНТСКОЕ (client_id NOT NULL + RLS по членству)
│     сотрудники/членства, заявки (purchase_*), письма (mailbox_*),
│     пометки и цены по поставщикам (client_supplier_notes / _prices),
│     вложения в Storage: clients/<client_id>/…
│
└── ВНУТРЕННЕЕ АНАТОЛИЯ (client_id = «redevelopment» или только platform_owner)
      лиды, финмодели, лендинги, БЦ/ТЦ, SEO-метрики, транзакции …
```

### 3.2. Схема изоляции — выбор: **`client_id` на таблицах + RLS** (не отдельные схемы)

| Критерий | Отдельная схема на клиента | **`client_id` + RLS** ✅ |
|---|---|---|
| Общая база поставщиков | нужны кросс-схемные связи и дубли справочников | обычные связи внутри одной схемы |
| Новый клиент | создать схему, прогнать все миграции, открыть схему в API Supabase | одна строка в `clients` + членства |
| Миграции | × количество клиентов, риск рассинхрона | одна миграция на всех |
| Supabase API / supabase-js | каждую схему надо отдельно выставлять в API и переключать в клиенте | работает как есть |
| Отчёты Анатолию по всем клиентам | UNION по схемам | обычный запрос под `platform_owner` |
| Надёжность изоляции | высокая | высокая **при** обязательном RLS + тестах (п. 3.7, 3.8) |
| Масштаб (единицы–десятки клиентов) | избыточно | подходит |

**Решение:** одна схема `public`, колонка `client_id` во всех клиентских таблицах, RLS-политики по членству. Отдельную схему/базу рассматриваем только для клиента, который потребует физического разделения по договору (вне этого блока).

### 3.3. Что изолируется (данные клиента)

| Данные | Таблицы (текущие → целевые) | Правило |
|---|---|---|
| Клиенты и членства | `clients`, `client_members` (новые, из блоков 1–2) | пользователь видит только свои членства |
| Сотрудники | профили + `client_members` | видны только коллегам по клиенту |
| Заявки (закупки) | `purchase_orders`, `purchase_order_events`, `purchase_documents`, `purchase_deliveries`, `purchase_delivery_addresses`, `purchase_receivers` | `client_id` обязательный |
| Письма | `mailbox_emails`, `mailbox_contacts`, `mailbox_email_templates`, `outgoing_email_jobs`, `unmatched_incoming_emails` | `client_id` обязательный; входящее письмо без определённого клиента — только `platform_owner` |
| Пометки поставщиков клиента | **новые** `client_supplier_notes` (пометки, рейтинг, статус «работаем/нет»), `client_supplier_prices` (полученные цены, КП) | `client_id` + `supplier_id` |
| Подрядчики клиента (если используются) | `work_contractors`, `work_contractor_emails`, `work_contractor_bulk_send_*` | `client_id` обязательный |
| Журнал действий | журнал из блоков 1–2 | клиент видит только свой; `platform_owner` — всё |
| Файлы | Storage: `clients/<client_id>/…` | доступ по членству; подписанные ссылки с ограниченным сроком |

### 3.4. Что общее (база поставщиков)

| Общее (одно на всех) | Клиентское поверх общего |
|---|---|
| `suppliers`: название, ИНН, сайт, контакты компании, категории, регион | `client_supplier_notes`: пометки, рейтинг, «работаем / не работаем», ответственный |
| `supply_categories`, `supply_terms`, `supply_catalog_reviews` | `client_supplier_prices`: цены, КП, сроки, привязка к заявке |
| `supplier_contacts`, `supplier_site_snapshots`, `supplier_screenshots`, `supplier_reliability_checks` | история заявок клиента с этим поставщиком (через `purchase_*`) |

- Читают общее — все вошедшие пользователи. Правит — только `platform_owner`.
- Клиент добавляет поставщика → запись в общей базе с `created_by_client_id` и статусом «на модерации»; до модерации видна только этому клиенту.
- Существующие личные поля в `suppliers` (заметки, оценки Анатолия) переносятся в `client_supplier_notes` клиента «redevelopment» (детали — блок 4).

### 3.5. Правила доступа в базе (RLS) — главный рубеж
- Для каждой клиентской таблицы: `SELECT/INSERT/UPDATE/DELETE` разрешены, только если `client_id` ∈ клиенты, где у пользователя активное членство.
- `INSERT`/`UPDATE`: `client_id` нельзя подменить на чужой (проверка в политике `WITH CHECK`).
- Роль внутри клиента: удаление и управление сотрудниками — только `client_admin`; `client_staff` — по правам из `TZ-admin.md`.
- `platform_owner` **не** получает автоматический доступ к данным клиента через админку клиента: в контексте клиента он — обычный член (`client_staff` в Матрёшке). Доступ ко всем клиентам — только через функции/представления админки платформы (только метаданные: клиенты, пользователи, журнал).
- Таблицы без `client_id` (общие) — отдельные политики: чтение всем вошедшим, запись — `platform_owner`.
- Внутренние таблицы Анатолия — доступ только `platform_owner`.
- Анонимный ключ (`anon`) клиентские таблицы не видит вообще; публичные токен-страницы читают только через свои узкие функции.

### 3.6. Сервер (`api/*`) и Storage
- Каждый запрос админки клиента несёт `client_id` (из домена `основа.redevelopment.pro` / `osnova.redevelopment.pro` / URL). Сервер проверяет членство и роль до любого действия. Нет членства → 403.
- По умолчанию `api/*` ходят в базу **от имени пользователя** (его JWT), чтобы RLS работал. `service_role` — только для явно перечисленных служебных задач (вебхуки почты, фоновые рассылки), и такие функции сами проставляют и проверяют `client_id`.
- Определение клиента для входящих писем (`purchase-email-webhook`): по адресу/ящику клиента; не определён → в «неразобранные» `platform_owner`.
- Storage: путь файла начинается с `clients/<client_id>/`; политики Storage проверяют членство так же, как RLS. Публичных бакетов с клиентскими файлами нет.

### 3.7. Автотесты изоляции
- Скрипт-аудит (развитие `scripts/audit-rls.mjs`): для каждой таблицы проверяет — есть ли `client_id` (если клиентская), включён ли RLS, есть ли политики на все 4 операции.
- Тест «два клиента»: тестовые клиенты A и B, пользователь A пытается читать/писать/удалять данные B напрямую через supabase-js и через `api/*` → везде 0 строк / 403.
- Запуск при каждом изменении миграций (перед мёржем в `oodobu` и перед ручным деплоем через Vercel CLI).

### 3.8. Критерии приёмки
1. Во всех клиентских таблицах (п. 3.3) есть обязательный `client_id`, индекс и RLS-политики на все 4 операции — аудит-скрипт зелёный.
2. Грузев (Матрёшка) видит только заявки, письма, пометки и цены Матрёшки; данных redevelopment и других клиентов не видит.
3. Прямой запрос Грузева через supabase-js к чужим данным → 0 строк; попытка записать чужой `client_id` → ошибка.
4. `api/*` админки клиента без членства → 403; без сессии → 401.
5. Общая база поставщиков видна и Матрёшке, и тестовому клиенту B; пометки/цены Матрёшки клиенту B не видны.
6. Поставщик, добавленный Матрёшкой, до модерации виден только Матрёшке; после — всем.
7. Анатолий в контексте Матрёшки видит ровно то же, что `client_staff`; данные Матрёшки через админку платформы не видны (только метаданные).
8. Внутренние таблицы Анатолия (лиды, финмодели, метрики и т.п.) недоступны пользователям клиентов.
9. Файл из заявки Матрёшки не открывается пользователем клиента B (ни по пути, ни по старой ссылке); подписанная ссылка истекает.
10. Входящее письмо по ящику Матрёшки попадает в Матрёшку; письмо без клиента — только в «неразобранные» у Анатолия.
11. Тест «два клиента» автоматически запускается перед мёржем в `oodobu` и проходит.
12. Публичные токен-страницы и сайты работают как раньше; скорость списков заявок/поставщиков — в пределах +20 %.

### 3.9. Как проверю вживую
- До мёржа: аудит-скрипт и тест «два клиента» на превью/тестовой базе; замер скорости списков «до» (база для +20 %).
- После «да» и деплоя через Vercel CLI — на проде под Грузевым и тестовым клиентом B: запросы supabase-js из консоли браузера к чужим таблицам → 0 строк; запись чужого `client_id` → ошибка; `curl` к `api/*` → 401/403; открытие чужого файла и просроченной подписанной ссылки → отказ; тестовое письмо в ящик Матрёшки → в Матрёшке; сайты и токен-страницы открываются; повторный замер скорости.

## 4. Критика

### 4.1. Риски и лучшие варианты
- **Переход `api/*` с `service_role` на JWT пользователя** — самая рискованная часть: затрагивает почти все функции и сайты (malllist, officelist, токен-страницы). Делать поэтапно, с перечнем функций и тестом на каждую; к понедельнику — только закупки и поставщики.
- **Рекурсия в RLS.** Политики, читающие `client_members`, на самой `client_members` зацикливаются — нужна `SECURITY DEFINER`-функция «мои клиенты» с фиксированным `search_path`.
- **`SECURITY DEFINER`-функции и представления** обходят RLS — каждую проверять в аудите, иначе дыра мимо политик.
- **«Автоматически перед мёржем»** — `.github/workflows/ci.yml` уже гоняет `npm run audit:rls` на PR и на пуш в `oodobu`, но на практике фичи пушатся в `oodobu` напрямую, то есть проверка срабатывает уже *после* попадания в ветку. Тест «два клиента» добавить в тот же CI и прогонять его до ручного деплоя через Vercel CLI (деплой только при зелёном CI).
- **+20 % скорости** без замера «до» не проверить — замерить до начала работ.
- **Внутренние данные под «redevelopment»:** Анатолий в Матрёшке — `client_staff`, а к своим данным ходит как `platform_owner` — убедиться, что переключение контекста не открывает внутренние таблицы в контексте клиента.
- **Старые публичные ссылки на файлы** продолжат работать, пока бакеты публичные — перенос в `clients/<client_id>/` и закрытие бакетов делать одной операцией с проверкой.

### 4.2. Открытые вопросы
- Цены поставщиков: может ли Анатолий (как владелец) видеть агрегированные цены всех клиентов для аналитики? Сейчас — **нет** (изоляция строгая).
- Нужен ли Матрёшке модуль подрядчиков (`work_contractors`), или в первой версии только закупки?
- Модерация новых поставщиков: Анатолий вручную или автоматически по ИНН?
- Ящик для писем Матрёшки: отдельный адрес на домене платформы или пересылка с их почты?
- Тест «два клиента» против какой базы в CI — отдельный тестовый проект Supabase или локальный Postgres?
