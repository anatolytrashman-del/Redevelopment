## Деплой

**Быстрый лендинг закупок (отдельно от сайта).** Статика
`public/pitch/zakupki/` выкладывается workflow
`.github/workflows/deploy-pitch-zakupki.yml` на GitHub Pages за десятки секунд,
без `npm` и пререндера:
`https://anatolytrashman-del.github.io/Redevelopment/pitch-zakupki/`.
Триггер — push в `oodobu` с правками в этой папке (environment `github-pages` сейчас пускает только эту ветку; `cursor/*` в policy добавит владелец в настройках GitHub, если понадобится деплой без мержа).
Прод `redevelopment.pro/pitch/zakupki` по-прежнему идёт обычным Vercel-деплоем.
Хелпер URL: `scripts/deploy-pitch-fast.sh`.


**Vercel → redevelopment.pro** — прод, единственная цель. Собирается автоматически при пуше в
`claude/redevelopment-platform-prototype-oodobu` (Vercel git-интеграция, вне репозитория,
конфигурации workflow для неё нет). Единственное место, где реально работают `api/*.js`.

**Сколько идёт билд и как за ним следить (2026-09-12).** Норма прод-билда для
правок админки/API — ~1 минута (пререндер и OG-обложки копируются с прода, см.
`scripts/prerender-snapshot.mjs`). Полный пререндер всех ~285 путей — ~6 минут
(общий браузер, 2 vCPU на машине сборки): законен только когда изменился код
публичных страниц (отпечаток `public-build-id`), сохранён бизнес-центр в
админке (`deploy_debounce.scope = business_centers`) или задан ручной
`PRERENDER_FORCE_FULL=1`. Сохранение объекта (`scope = objects`) даёт ЧАСТИЧНЫЙ
режим — заново рендерятся только лендинги объектов, ~1 минута.

**Сохранение в админке сборку НЕ запускает (с 2026-09-19).** Оно только
ставит отметку в `deploy_debounce`; саму пересборку раз в час дёргает
`pg_cron` (`rebuild-public-pages`, `13 * * * *`), и только если отметка есть.
Раньше хук дёргался прямо из сохранения с дебаунсом 5 минут — за долгий
сеанс правок БЦ это давало полную пересборку каждые 5-6 минут часами
(разбор — в `api/trigger-rebuild.js`). Правки не теряются: `scope`
накапливается, ближайшая сборка забирает отметку атомарно. Цена — публичные
страницы догоняют базу в пределах часа, а не сразу.

Всё остальное долгое — баг: в Build Logs искать строку `[prerender] ИТОГ … режима` (число
«из-за непригодной копии» в норме 0, ниже — причины) и строку `[prerender]
… режим (<причина>)`.
В окружении сессии есть `VERCEL_TOKEN`, `api.vercel.com` открыт (`vercel.com` —
нет): `GET /v6/deployments?app=redevelopment&limit=10` — список со `state`,
`GET /v3/deployments/<id>/events?builds=1` — лог сборки построчно.
Ждать деплой только опросом с выходом по ЛЮБОМУ терминальному состоянию
(`READY`, `ERROR`, `CANCELED`) и с потолком ~15 минут: цикл, ждущий только
`READY`, на упавшем билде висит до таймаута — ровно то, что владелец видел как
«деплой висит 20 минут».

**Сборка вне Vercel в базу не ходит (с 2026-09-24).** CI и сессии берут
данные из снимков и с прода (`buildDataOffline()` в `scripts/_buildFallback.mjs`),
живая база — только с `BUILD_DATA_LIVE=1`. Иначе ~250 проверочных сборок в
сутки съедали ~¾ трафика Supabase. Расход смотреть
`node scripts/supabase-egress-report.mjs`. Цель владельца с 2026-09-24 — бесплатный
тариф (5 ГБ/мес), поэтому фоновый опрос в админке — только «новое после
отметки» (`src/lib/backgroundPoll.ts`) или отметки изменений таблиц
(`src/lib/changeStamps.ts`), а не перекачка списка; прод-сборка качает
каталог из базы, только если сдвинулись отметки (`/data/catalog-stamps.json`).

**Превью до прода (с 2026-09-17).** `preview` — общая ветка сборки превью, куда
сливается ВСЯ работа по каталогу БЦ: владелец с 2026-09-17 ведёт эти правки сам,
в Codex Cloud или приложении через GitHub с базовой веткой `preview`.
По явному разрешению владельца от 2026-09-17 Codex сам мержит свои PR в
`preview` после успешного CI; production остаётся отдельной публикацией.
Это правило имеет приоритет над общими запретами мержа для Codex ниже. Claude
в `preview` не форс-пушит (затрёт чужое) — вливает свою ветку мержем. Из `preview`
в прод переносит только Claude, разом и после приёмки. Владелец смотрит правки
на этой ветке, а не на живом сайте: мерж проверенного PR в `preview` → стабильный адрес
`https://redevelopment-git-preview-redevlopment.vercel.app` (под логином владельца,
`noindex`). Замеры 2026-09-17: превью — 1 мин 20 с, прод с изменёнными публичными
страницами — 7–8 мин, прод без них — 1,5 мин. Разница в том, что превью-сборка
НИКОГДА не идёт в полный пререндер (`scripts/prerender.mjs:698`) и копирует разметку
с прода. Отсюда и оговорка: статика первого экрана на превью может быть старой,
JS-бандл свежий — для визуальной проверки правок годится, для проверки самого
пререндера и SEO-разметки нет. Порядок: пачка мелких правок → `preview` → «ок»
владельца → один PR в прод. Открыта ровно одна ветка `preview`
(`vercel.json` → `git.deploymentEnabled`), и читается этот ключ из vercel.json
ПРОД-ветки: правка, лежащая только в ветке сессии, не включает сборку.

**Фоновые очереди живут в Supabase, не в GitHub Actions (с 2026-09-11).**
Шесть Edge Function в `supabase/functions/`: `process-supplier-jobs` разбирает
веб-поиск (`supplier_web_search_jobs`) и обогащение контактов
(`supplier_enrichment_jobs`), `process-bulk-send-jobs` — массовую рассылку
(`bulk_send_jobs`/`bulk_send_job_items`), `process-outgoing-emails` — досылку
одиночных писем (`outgoing_email_jobs`), `process-followups` — дожим молчащих
поставщиков (раз в ЧАС, `17 * * * *`; рубильник
`email_auto_reply_settings.followups_enabled`, по умолчанию выключен).
Плюс два синка статистики сайта, переехавшие сюда с крона GitHub Actions
2026-09-16: `sync-yandex-metrika` (раз в час, `37 * * * *`) и
`sync-yandex-webmaster` (раз в сутки, `47 5 * * *`) — обе пишут в таблицы,
которые читает страница «Показатели». Первые три дёргает `pg_cron` раз в
минуту через `pg_net` (ключ для вызова лежит в Vault под именем
`edge_service_role_key`), остальные — тем же способом по своему расписанию. Секреты функций — `PROXYAPI_KEY` и `RESEND_API_KEY`
(в секретах проекта Supabase, не в репозитории).
Деплой функции: `POST /v1/projects/<ref>/functions/deploy?slug=process-supplier-jobs`
с тем же `SUPABASE_ACCESS_TOKEN`, что и SQL-миграции. Одноимённые скрипты в
`scripts/` и воркфлоу остались как ручной запасной путь (`workflow_dispatch`,
без крона) — запускать их «чтобы побыстрее» не нужно, очередь и так
разбирается раз в минуту. У ДВУХ СИНКОВ ЯНДЕКСА второй копии кода нет
сознательно: их воркфлоу (`sync-yandex-metrika.yml`,
`sync-yandex-webmaster-stats.yml`) — это кнопка «запустить руками», которая
`curl`'ом дёргает ту же функцию. Дублировать 400 строк логики в двух
рантаймах — гарантированное расхождение, см. про файлы-близнецы ниже. У массовой рассылки ручной путь до 2026-09-12
захвата НЕ делал, и параллельный запуск разослал по два письма 38
поставщикам; теперь атомарный захват строки задания есть в обоих воркерах
плюс уникальный индекс по `supplier_offer_emails.bulk_job_item_id` — порядок
«захват → проверка → отправка» править сразу в обоих файлах.
Почему так: GitHub затроттлил Actions аккаунта за три крона раз в 5 минут на
бесплатном публичном репозитории (см. docs/session-journal.md, 2026-09-11).
Крон Actions вообще не расписание, а пожелание: синк Метрики с `0 23 * * *`
реально ходил в 00:47/01:08/01:12 — из-за этого «Показатели» показывали
вчерашний день (2026-09-16). Новую периодическую задачу заводить сразу в
`pg_cron`, а не в Actions. Денег это не стоит: бесплатный план Supabase
включает 500 000 вызовов Edge Functions в месяц, шесть текущих функций
расходуют ~133 000.

Нужные env-переменные на Vercel (секреты, не в репозитории):

```
SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY      — server-side доступ в обход RLS (api/*.js)
RESEND_API_KEY, RESEND_FROM                  — письма с OTP-кодом подписания
GOOGLE_OAUTH_CLIENT_ID / _SECRET / _REFRESH_TOKEN
INTENT_AGREEMENT_TEMPLATE_ID                 — id гугл-шаблона "соглашение о намерениях" (покупка кабинета)
WORKSTATION_AGREEMENT_TEMPLATE_ID            — тот же документ, но для рабочих мест (покупка)
RENT_AGREEMENT_TEMPLATE_ID                   — то же самое соглашение, но текст про аренду кабинета
                                                (2026-09-13+, см. docs/session-journal.md)
RENT_WORKSTATION_AGREEMENT_TEMPLATE_ID       — аренда рабочего места (2026-09-13+)
TELEGRAM_BOT_TOKEN, TELEGRAM_WEBHOOK_SECRET, TELEGRAM_ALLOWED_USER_IDS
                                              — бот-копилка: пересланное из личных диалогов
                                                (docs/telegram-capture-bot.md)
KUFAR_BEARER_TOKEN, REALT_COOKIE, AVITO_COOKIE, MEGAPOLIS_COOKIE
                                              — авторизация в scripts/sync-*-stats.mjs
                                                (крон раз в час, см. sync-demand-stats.yml)
```

**Новый секрет кладём сразу в ТРИ места** (правило владельца, 2026-09-16):
переменные окружения сессии (настройки окружения Claude Code на вебе), Vercel
(Production) и GitHub → Settings → Secrets and variables → Actions. Даже если
прямо сейчас его читает только одна из трёх сторон: искать потом, где лежит
ключ и почему не работает, дороже, чем вставить его три раза. В окружении
сессии переменная появляется только в СЛЕДУЮЩЕЙ сессии, не в текущей.

`.env.example` — только для **клиентских** VITE_-переменных (необязательно, в
`src/lib/supabase.ts` уже зашит рабочий проект по умолчанию).
