# SEO-финализация раздела бизнес-центров

Повод: владелец, 2026-09-22 — «закончил 98% каталога БЦ, дальше только мелкие
правки; хочу сделать SEO-оптимизацию и финально подготовить раздел для
поисковиков, за основу берём всё, что делали по странице аналитики Минск Мира».
Объём согласован тогда же: **весь раздел БЦ целиком** — корень `/minsk/bcminsk`,
все хабы (класс, район, класс+район, микрорайон, метро, улица, строящиеся),
141 карточка здания и страницы `/gid`, `/analytics`, `/rating*`.

Спидтесты владелец досылает отдельно — шаг про вес страниц ждёт их.

---

## Что показал аудит (факты, а не догадки)

Прогон 2026-09-22: `curl` по всем 266 URL раздела из `sitemap.xml` + граф
внутренних ссылок по всем 286 страницам сайта.

**Уже в порядке (не трогаем):**

- 266/266 отдают 200, у всех `<h1>`, текст и FAQ есть прямо в HTML (пререндер
  работает), `robots: index, follow`, canonical на себя.
- Ни одного дубля `title` и ни одного дубля `description` на 261 индексируемой
  странице. Длины: title 35–66 символов (ширина считается в пикселях,
  `serpTitleWidth.ts`), description 123–254 символа.
- `og:image` у каждой страницы свой (`/og/minsk-bcminsk-*.png`), 1200×630.
- Хабы: `Article` + `BreadcrumbList` + `FAQPage` + `Organization` + `WebPage`.
  Карточки: `RealEstateListing` + `Place` (+ `LocationFeatureSpecification`) +
  `FAQPage` + `BreadcrumbList`.
- FAQ предпоследним блоком, «Источники» последним — как на аналитике Минск Мира.
- `sitemap.xml`: 286 URL, у каждого `lastmod`/`changefreq`/`priority`.
- Число FAQ-вопросов на страницу: 7–15 (на одной 40), пустых нет.

**Находки, с которыми и работаем:**

1. **Нет `ItemList` на 261 странице каталога.** Разметка листинга есть только на
   пяти страницах рейтингов (`setItemListJsonLd` в `BusinessCentersRanking*`,
   `Biggest`, `Affordable`). Сам каталог и все его хабы — перечень зданий без
   разметки перечня.
2. **48 URL в sitemap без единой входящей ссылки.** Проверено по графу ссылок
   всех 286 страниц: 19 хабов улиц, 18 хабов «класс + район», 11 хабов
   микрорайонов. Все они маленькие — 1–4 здания. Причина: блоки рекомендаций на
   карточке БЦ показываются, только если в том же срезе есть ДРУГИЕ здания, и
   число блоков на карточке ограничено, а ковёр чипов-срезов с видимой части
   сайта убран 2026-09-22 сознательно. Итог: страницы есть в индексе-кандидатах,
   но вес по ним не течёт, а контент на них тонкий.
3. **Пустые теги JSON-LD в HTML карточек.** `article-json-ld`,
   `dataset-json-ld`, `itemlist-json-ld`, `organization-json-ld` лежат в
   `index.html` как слоты и на страницах без такой разметки остаются пустыми.
   **Осознанно не чиним:** удалять слот из снапшота нельзя — после гидратации
   `setXJsonLd` ищет его по `getElementById`, и при SPA-переходе разметка
   просто не проставится. Пустой `<script>` валидаторы игнорируют, реального
   дефекта тут нет. Что действительно чинилось — пустой `FAQPage` (п. 7):
   это не пустой слот, а невалидная разметка.
4. **Четыре description длиннее 160 символов** (максимум 254) — бюджет
   `DESCRIPTION_BUDGET = 160` на них не сработал.
5. **Вес страниц:** медиана HTML 134 КБ, p90 189 КБ, максимум 257 КБ
   (`/class/b` и корень каталога). На корне 163 инлайн-SVG. Это то, на что
   ругался тех-аудит (`BC_CATALOG_TECH_AUDIT.md`, п. 1).
6. **Мета отфильтрованных состояний была чужой.** Любой URL каталога с
   query-фильтром (`?class=A&metro=…`) пререндером не снимается, отдаётся
   SPA-оболочка — и до правки на нём оставались ДЕФОЛТНЫЕ теги `index.html`:
   заголовок, описание и `og:image` объекта Red One, `canonical` на
   `/minsk/one`. То есть ссылка на отфильтрованный каталог разворачивалась в
   мессенджере превью другого объекта, а canonical указывал на чужую
   страницу — хотя по замыслу он всегда должен вести на хаб.
7. **Пустой `FAQPage` вместо отсутствия разметки.** `setFaqJsonLd([])`
   записывал скелет `{"@type":"FAQPage","mainEntity":[]}` — на soft-404,
   на состояниях под фильтром и при любом SPA-переходе на страницу без FAQ.
8. **Незакрытые кластеры из тех-аудита:** фильтра «с парковкой» нет;
   «заполняемость/вакантность» живёт внутри `/analytics`, не на своём URL;
   кластер «отзывы о бизнес-центрах» не закрыт ничем.

Отдельно: `aggregateRating` на карточках НЕ добавляем — это осознанное решение
из `BCMINSK_SEO_PLAN.md` (чужие оценки показываем, но не выдаём за свой агрегат).

## Найдено попутно, вне раздела БЦ

**`/minsk/one` не получает НИ ОДНОЙ внутренней ссылки.** Проверено 2026-09-22
по всем 257 страницам sitemap: ни одна на неё не ссылается. Корень `/` отдаёт
307 на `/minsk`, а на самом `/minsk` ссылки на объект нет. То есть страница
продающего объекта Red One — цель всего сайта — держится в индексе только на
sitemap и внешних переходах, внутреннего веса не получает вовсе. Это вне
согласованного объёма (раздел БЦ), поэтому не чинил: решение владельца.

## Шаги

- [x] **Ш1. Разметка листинга и мета.** Сделано 2026-09-22: `ItemList` на
      каталоге и всех его хабах (ровно то, что отрисовано в сетке; после
      «Показать ещё» список в разметке растёт вместе с сеткой), своя мета и
      canonical на хаб у состояний под фильтром, `setFaqJsonLd([])` больше не
      пишет пустой `FAQPage`, три описания приведены в 160 символов
      (`/gid` 254 → 158, `/analytics` 207 → 156, `/rating` 178 → 151).
- [x] **Ш2. 48 страниц-сирот.** Владелец, 2026-09-22, выбрал «разделить:
      линкуем крупные, закрываем мелкие». Сделано:
      блок «Смежные подборки» на хабе района (классы, микрорайоны, улицы) и
      на хабе класса (районы) — только ссылки на срезы от
      `MIN_INDEXABLE_HUB_CENTERS = 3` зданий, на корне каталога блока нет;
      срез улицы, микрорайона или «класс + район» с 1–2 зданиями получает
      `noindex` (без разметки Article/ItemList/FAQ) и выпадает из sitemap —
      29 URL, файл со 286 сократился до 257. По ссылке такие страницы
      по-прежнему открываются и пререндерятся, из индекса убран только
      сигнал «иди сюда». Порог и карты слагов продублированы в
      `scripts/generate-sitemap.mjs` (скрипт без TS-загрузчика) — копии
      сверяет тест в `businessCenterHubs.test.ts`.
- [x] **Ш3-a. Вес данных: 969 КБ → 149 КБ.** Сделано 2026-09-22. Замер
      Lighthouse (мобильный профиль, CPU ×4) показал не вес HTML, а другое:
      каждая страница раздела тянула `business_centers?select=*` — 969 КБ
      сжатых, 3,17 МБ JSON, тело ответа ~3,8 с. Всё это время страница
      стояла с «Загрузка…» ВМЕСТО уже отрисованной пререндером разметки:
      каталог схлопывался с 8371 px до 968 px примерно на 2 секунды,
      карточка БЦ — с 13 628 px до 727 px. Отсюда CLS 0,22–0,29 на всех
      страницах каталога и Speed Index 3–5 с. Теперь список забирает только
      нужные колонки (`LIST_COLUMNS`), карточка догружает свой ряд отдельно
      (`fetchBusinessCenter(slug)`), админка — полную таблицу
      (`fetchBusinessCentersFull`). Число арендаторов для сравнений вынесено
      в generated-колонку `tenant_count`. Содержимое страниц не изменилось:
      сверено посимвольно со старым кодом на карточках и хабах.
- [ ] **Ш3-b. Пустое окно при гидратации.** Даже с быстрым ответом React
      на старте подменяет готовую разметку пререндера состоянием
      «Загрузка…». Радикальное лечение — отдавать данные вместе со
      снапшотом (инлайн-JSON) или не гидратировать до их прихода. Мерить
      после Ш3-a: возможно, окна уже почти нет.
- [x] **Ш3-c (картинки). srcset для карточных фото.** Сделано 2026-09-22 по
      отчёту PageSpeed владельца: «Улучшите загрузку изображений — экономия
      1417 КиБ», крупнейшая потеря страницы. Замер на живой странице: на
      десктопе 1440 фото карточки занимает 241 CSS-px при DPR 1 — файл
      640×640 избыточен в 2,7 раза; телефону 360 при DPR 3 нужно 468.
      Пережимать бессмысленно (файлы уже прогнаны TinyPNG, повтор даёт −7 %),
      поэтому сделаны уменьшенные копии 320 и 512
      (`scripts/generate-card-image-variants.mjs`) и `srcset`/`sizes` в
      `PhotoBlock`. Браузер берёт: десктоп DPR 1 — 320 (20 КБ), телефон
      DPR 2/3 — 512 (38 КБ), планшет DPR 2 — 640 (69 КБ). Наличие копий у
      каждого фото проверяет тест: без них `srcset` увёл бы браузер на
      несуществующий файл, а на `src` он не откатывается.
- [ ] **Ш3-d. Вес самого HTML.** Медиана 134 КБ, максимум 257 КБ
      (`/class/b` и корень каталога), 163 инлайн-SVG на корне. Плюс из
      отчёта владельца: период хранения кеша (92 КиБ), устаревшие полифилы
      (21 КиБ), блокирующий CSS (120 мс).
- [ ] **Ш4. Новые кластеры.** Заполняемость на своём URL, отзывы, фильтр
      «с парковкой» — каждый пункт отдельным решением.
