## Диагноз (что видно на проде 2026-09-16)

Каталог, десктоп 1440 px:
- Первая карточка БЦ появляется примерно на 1900-м пикселе: над ней hero с
  фото (`HERO_IMAGES`), «Рынок в цифрах» (8 плиток), «Ставки аренды и продажи»
  (2 плитки) и пустая заглушка карты («Показать карту»). На первом экране
  ноль бизнес-центров.
- Левый фильтр длиннее трёх экранов: Район (10), Микрорайон (18), Класс
  (пилюли), Метро (8 + «ещё 24 станции»), Улица (8 + «ещё 15 улиц»), Статус и
  список ВСЕХ 143 названий БЦ. Каждая ось — отдельный SEO-URL, и клик по одной
  оси сбрасывает другую; комбинируются только класс×район (хаб) и станции
  метро (клиентские чек-боксы `metroSelection`).
- Нет сортировки, поиска, вида таблицей, цены/рейтинга на карточке.
  143 карточки по 3 в ряд — 48 рядов скролла, карточки одинаковые (фото +
  5 строк фактов + «Подробнее»).
- Мобильный: на headless-скриншоте ширины 390 (без эмуляции мобильного)
  контент выглядит шире экрана — **проверить на реальном телефоне**, может
  быть артефактом снимка.

Карточка БЦ («Виктория Плаза»):
- Содержательна, но это справочник: hero → 4 плитки → таблица техпараметров
  prometr.by без интерпретации → «Интересные факты» → организации → условия
  для арендаторов → объявления (2 лота продажи, аренды нет) → FAQ → источники.
- Ни одной сравнительной цифры (кроме одной строки «ниже медианы класса B на
  18%» под объявлениями), нет карты здания, соседей, похожих БЦ, вердикта
  «кому подходит», навигации по странице (8 длинных блоков).

Авторский подход Минск Мира, которого здесь нет: каждое число рядом с базой
сравнения и выводом (плотность 427 чел/га против 57 по городу и норматива
290), цветные плитки-тепловая карта, честные оговорки о пробелах данных,
кастомные блоки под тему, а не фиксированный шаблон.

Что взять у nomads.com (сайт из песочницы заблокирован, описание по памяти):
панель чипов-тумблеров с живыми счётчиками; мгновенная клиентская
фильтрация без перезагрузки; ранг и подшкалы прямо на карточке (полоски
при наведении); вид списком/таблицей; вкладки в карточке города (Scores,
Pros & Cons, Cost, Reviews, Near, Similar); открытая методика скоринга;
состояние фильтра в URL.

## Волна 4 — арендаторы как данные каталога (решено 2026-09-19)

Решение владельца 2026-09-19: **основной источник организаций в здании —
Яндекс.Карты, не 2GIS**. Причина в цифрах: яндексовский срез
(`business_center_tenant_source_snapshots`, source `yandex_maps`, собран
18–19.09 полуавтоматическим `scripts/capture-yandex-bc-tenants.mjs`) — это
7608 организаций по 139 зданиям против 4614 по 138 у 2GIS, и на организацию
есть этаж (57%), офис/секция (31%), рейтинг и число оценок (45%), ссылка на
карточку. У 2GIS на организацию только название и рубрика, плюс жёсткий
потолок выдачи в 50 организаций на здание, из-за которого у 26 зданий доли
считались по неполному списку.

Отдельные URL на каждую организацию — **решено не делать** (разбор
2026-09-19): на организацию есть только название, рубрика, рейтинг и этаж,
ни телефона, ни сайта, ни описания; запрос «<название компании> Минск»
навигационный и его забирают сами Яндекс.Карты, 2ГИС и сайт компании;
7,6 тыс. тонких страниц при 58 страницах в индексе Яндекса и половине
проверенных URL в статусе «Discovered — currently not indexed» меняют
профиль сайта не в ту сторону; пререндер (~1,3 с на путь) вырос бы с 6 минут
до 2,5–3 часов. Ценность тех же данных снимается двумя пунктами ниже.

- [x] **Б13. Яндекс как основной источник блока «Кто сидит в здании»** (сделано 2026-09-19).
      Организации берутся из яндексовского снапшота, 2GIS остаётся фолбэком
      для зданий, которых в нём нет, а старый список из веб-архива — вторым
      фолбэком. Что добавляется к нынешнему блоку: этаж и офис у организации,
      рейтинг и число оценок, ссылка на карточку в Яндексе, отдельная строка
      «сервисы в здании» (туалеты, кофейные автоматы, пункты выдачи,
      банкоматы — ~250–400 записей из 7608, в отраслевую диаграмму их не
      считать, иначе «организаций в здании» врёт).

      поиском, фильтром и страницами остался от неё, разбор по отраслям и

      «направления» фильтра — статическая группировка тех же 28 отраслей.

      Развилка, которую пришлось решить: отрасль у 2GIS — готовый `parent_id`
      общей рубрики (28 штук), а Яндекс отдаёт только текст рубрики (1559
      разных значений после чистки). Значит нужна карта «текст рубрики →
      отрасль», и она должна жить **в одном месте**. Живёт в TS
      (`src/lib/tenantCategories.ts`), потому что её читает фронт; поэтому
      городской профиль для сравнения «здание против каталога» пересчитывать
      в SQL по отраслям нельзя — SQL пришлось бы держать вторую копию карты
      (ровно тот случай файлов-близнецов, от которого предостерегает
      `CLAUDE.md`). Вместо этого SQL складывает городской срез **по рубрикам**
      (`refresh_bc_tenant_city_categories()`), а в отрасли его сворачивает та
      же TS-карта на клиенте.
