# Связка Claude ↔ Codex (ChatGPT Pro)

Заведено 2026-09-17, когда недельный лимит Claude просел до 13%, а владелец купил
подписку ChatGPT Pro. Цель — переложить на Codex ту часть работы, которая не требует
живых секретов и живой базы, и тратить лимит Claude только на постановку задач,
миграции, деплой и приёмку.

Правила для самого Codex лежат в `AGENTS.md` в корне — он читает их автоматически.
Этот файл про то, КТО что делает и КАК задача доезжает от Claude до Codex.

## Что важно знать про тарифы

Подписка **ChatGPT Pro не включает API-доступ**: `platform.openai.com` тарифицируется
отдельно, по токенам. Зато Pro включает **Codex** — он же ходит под аккаунтом ChatGPT
и ест лимит подписки, а не отдельный счёт. Поэтому связка строится на Codex, а не на
OpenAI API. Заводить `OPENAI_API_KEY` имеет смысл, только если понадобится вызывать
модель из кода прода (сейчас такой нужды нет — там ProxyAPI и Claude).

## Три канала, по убыванию автономности

### 1. `codex` CLI прямо в сессии Claude (полная автоматика)

> Статус на 2026-09-17, ночь: **канал проверен и работает, это основной путь.**
> `CODEX_AUTH_JSON` доехал, `scripts/codex.sh` восстановил `auth.json`, CLI
> поставился сам, Codex ответил и на вопрос, и на настоящее задание — правки
> легли в рабочее дерево, Claude их принял, собрал и выпустил на прод.
> Модель, на которой ходит Codex CLI под подпиской Pro, — `gpt-6-astra`.
>
> **Две вещи, без которых канал молча не работает** (обе уже исправлены, но
> знать про них надо, если что-то сломается):
>
> 1. `codex exec` по умолчанию идёт в **`sandbox: read-only`** — Codex «выполняет»
>    задачу и рапортует об успехе, а файлов не меняет ни одного. Обёртка теперь
>    передаёт `--sandbox workspace-write` (переопределяется `CODEX_SANDBOX=`).
> 2. В свежем контейнере Claude **`node_modules` пуст**, и `npm run build:app`
>    падает на `Cannot find type definition file for 'vite/client'` / `'node'` /
>    `@vercel/functions`. Это не поломка кода и не вина Codex: перед запуском
>    задания делать `npm ci` (6 секунд), иначе Codex не сможет проверить сборку
>    и честно отпишется, что она упала.
>
> Предупреждение `Codex could not find bubblewrap on PATH` — не ошибка: CLI
> берёт свой встроенный bubblewrap и работает.
>
> **Проверка канала (первое, что делает новая сессия):**
>
> ```bash
> env | grep -c CODEX_AUTH_JSON        # 1 — переменная доехала, 0 — нет
> npm ci                                # иначе Codex не соберёт проект
> scripts/codex.sh "Ответь одним словом: готов"
> ```
>
> `0` в первой строке означает, что переменная не сохранилась или окружение её
> не отдало, — это к владельцу, само не починится. Ошибка `codex.sh` про
> непохожий на JSON и base64 ввод — значит в переменную попало что-то лишнее
> (заголовок из заметок, обрезанная строка), лечится повтором
> `base64 < ~/.codex/auth.json | tr -d '\n' | pbcopy`.
>
> **Как отдавать настоящее задание.** Просто
> `scripts/codex.sh -f docs/codex-tasks/<задача>.md` — больше ничего готовить не
> надо. Файлы заданий написаны под облачный Codex и велят завести ветку и открыть
> PR; в канале 1 это не так, поэтому обёртка сама подклеивает к любому ТЗ из файла
> приписку `docs/codex-tasks/_cli-addendum.md` с правилами канала: работать в
> текущей ветке, коммитить и пушить можно, PR и мерж — не его, `npm ci` не
> запускать, `npm run build:app` прогнать. Правила канала поменялись — правится
> этот файл, а не промпт в каждой сессии.
>
> **PR в канале 1 Codex открыть не может: `gh` в контейнере нет.** Он коммитит и
> пушит ветку, PR открывает Claude через GitHub MCP, он же мержит и ждёт деплой.
>
> Установка CLI на macOS: `npm i -g @openai/codex` упирается в EACCES на
> `/usr/local/lib` — это права, а не поломка. Ставить `brew install codex`
> (официальная формула) либо, если brew нет, `sudo npm i -g @openai/codex`.
> У владельца CLI уже стоит (0.154.0) и залогинен — `codex login status`
> отвечает «Logged in using ChatGPT».

Claude зовёт Codex из Bash как субагента и сам принимает результат. Требует:

- в Allowed domains окружения: `chatgpt.com`, `auth.openai.com`, `api.openai.com`
  (первый — основной, через него Codex CLI ходит в бэкенд под аккаунтом ChatGPT);
- переменную окружения `CODEX_AUTH_JSON` — содержимое `~/.codex/auth.json` с машины,
  где владелец один раз выполнил `codex login` («Sign in with ChatGPT»), **в base64**:

  ```
  base64 < ~/.codex/auth.json | tr -d '\n' | pbcopy
  ```

  Почему base64, а не сырой JSON: поле переменных в настройках окружения — формат
  `.env`, одна строка `KEY=value`. `auth.json` многострочный, с кавычками и пробелами,
  и вставленный как есть ломает разбор («Couldn't parse … Use KEY=value format»,
  проверено 2026-09-17). Обёртка понимает оба вида, но руками вставлять надо base64.
  Строка целиком выглядит так: `CODEX_AUTH_JSON=<длинный base64 без пробелов>`.
  Это учётные данные аккаунта ChatGPT: не печатать в чат и в логи, не коммитить.
  Переменная окружения сессии подхватывается только СЛЕДУЮЩЕЙ сессией, не текущей.

Дальше работает обёртка `scripts/codex.sh` — она восстанавливает `auth.json`, при
необходимости ставит CLI и запускает задачу:

```bash
scripts/codex.sh "Перепиши фильтр поставщиков в src/pages/Suppliers.tsx на ..."
```

## Кто берёт задачу: Claude или Codex (правило отбора, 2026-09-17)

Владелец: «ты даже сам можешь оценивать по объёму, какую задачу брать самому, а
какую отдавать Codex». Оценивает Claude, спрашивать разрешения на каждую задачу не
надо. Мерка — не «сложно/просто», а **сколько строк ТЗ придётся написать против
того, сколько строк кода получится**:

- **Правка меньше ~50 строк, или файлы уже в контексте сессии, или объяснять
  контекст дольше, чем сделать** → Claude делает сам. Проверено на задании К-1:
  ТЗ вышло на 60 строк ради 14 строк кода — чистый убыток, отдавать такое Codex
  бессмысленно.
- **От ~100 строк, несколько файлов, незнакомая область, рутина вроде вёрстки,
  тестов и типизации** → Codex. Здесь приёмка (диф + чек-лист) реально дешевле
  написания.
- **Между** — решает объём объяснений: много контекста придётся пересказывать,
  значит дешевле сделать самому.
- **Всегда у Claude, независимо от объёма:** живая база, секреты, миграции,
  Resend, Vercel, Edge Functions, деплой и мерж.

**Пакетный режим.** Один прогон Codex = 2–3 задания из очереди подряд, одна
приёмка, один PR, один деплой. Гонять по одному заданию за PR — три ожидания
сборки вместо одного.

## Кто что делает

**Codex забирает:** изолированные правки фронта по готовому ТЗ, рефакторинг,
вёрстку и адаптив, тесты (vitest), типизацию, разбор и чистку мёртвого кода,
генераторы в `scripts/`, текстовый SEO-контент, подготовку SQL-файлов миграций.

**За Claude остаётся:** всё, где нужны секреты и живые сервисы — применение миграций
через Supabase Management API, разовые прогоны по живой базе, разбор почты Resend,
Edge Functions в Supabase, наблюдение за деплоем Vercel, мерж PR, журнал сессий,
приёмка работы Codex.

**Пограничное — решает Claude:** если задача требует знать поведение живых данных
(сколько там строк, какие значения реально встречаются), Codex сделает вслепую и
ошибётся. Такие задачи либо остаются у Claude, либо Claude сначала снимает срез
данных и кладёт цифры прямо в ТЗ.

## Формат ТЗ для Codex

Codex не видел этот диалог и стартует с чистого листа. В задаче обязаны быть:

1. **Цель** одним абзацем — что должно получиться с точки зрения пользователя.
2. **Файлы** по путям от корня репозитория — где смотреть и что править.
3. **Ограничения** — что трогать нельзя, какие правила из `AGENTS.md` тут критичны.
4. **Критерий готовности** — «чистый `npm run build:app`» плюс что должно измениться
   на экране или в данных.
5. **Контекст из живой базы**, если он нужен, — цифрами, а не отсылкой «посмотри в БД».

## Приёмка

**Механику проверяет CI, не Claude.** В репозитории есть `.github/workflows/ci.yml`
с триггером `pull_request`: `npm run lint`, `npx tsc -b`, `npm test`, полный
`npm run build` и `npm run audit:rls`. Повторять это руками на каждом задании не
надо — достаточно одного `npm run build:app` локально перед коммитом (10 секунд) и
зелёного CI на PR.

**Руками Claude смотрит только то, чего компилятор и тесты не ловят** — ровно те
грабли, на которых проект уже наступал. Код с ними собирается, тесты зелёные, а
ломается тихо и на проде:

1. выборка, где строк может стать больше 1000, — идёт ли она постранично через
   `.range()` (без него хвост теряется МОЛЧА: так пропали 141 поставщик и 393
   снимка сайтов);
2. запись даты — через `value || null`, иначе очистка поля падает на
   `invalid input syntax for type date`;
3. `!value` на числовом поле — `0` не должен читаться как «не заполнено»;
4. вложенная модалка — её быть не может, форма показывается ВМЕСТО тела текущей
   модалки с кнопкой «Назад»;
5. файлы-близнецы `src/` ↔ `api/` ↔ `supabase/functions/` — правлена ли вторая
   сторона (НДС, пороги дожима, захват задания рассылки);
6. палитра статусов — нейтральный статус не выкрашен в `primary` (фирменный
   красный неотличим от «опасно»).

Плюс беглый взгляд, что Codex не сделал лишнего сверх ТЗ и не тронул
`.github/workflows/`.

**Мерж — только Claude, это не обсуждается.** Мерж в `oodobu` = автодеплой на живой
redevelopment.pro, и это единственная дверь туда. Codex не видит живую базу (не знает,
что в таблице 1400 строк), не имеет доступа к Vercel и не увидит, что деплой упал.
Стоит эта дверь Claude пару тысяч токенов — экономить на ней нечего.
Владельцу это объяснено 2026-09-17, когда он спросил, не дать ли Codex право
заливать самому: до PR — можно всё, мерж — нет.

Описание PR и запись в журнал делать **коротко**: что за задание, ссылка на файл ТЗ,
что Codex решил иначе и почему. Пересказывать его работу абзацами не надо — диф и так
в PR.

SQL-файл из PR применяется отдельно, до мержа кода, и должен быть совместим со старым
кодом.
