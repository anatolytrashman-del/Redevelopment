# Модуль закупок как отдельный продукт — аудит и список улучшений

Дата: 2026-09-15. Заказ владельца: «начать продавать модуль закупок как
отдельный продукт для компаний в сфере недвижимости и строительства. На
выходе — инструмент, который помогает в пару кликов запросить цены со всего
рынка, быстро и автоматически сравнить цены и организовать поставку/закупку.
Удели внимание карточке поставщика, сейчас она похожа на заготовку».

Как собран этот документ: пять параллельных аудитов кода (страница и карточка
поставщика; сравнение цен и заказы; почтовый конвейер; поиск, обогащение,
верификация и каталог; журнал сессий), запросы к живой базе (счётчики строк,
воронка по категориям, распределение статусов), обзор конкурентов через
веб-поиск. Ссылки на код — файл:строка на коммите `fc3af9b`.

Структура: §1 диагноз и цифры → §2–§4 предложения по трём обещаниям продукта
(запросить / сравнить / организовать поставку) → §5 карточка поставщика →
§6 каркас продукта (мультиарендность, почта, конвейер) → §7 надёжность и
право → §8 конкуренты → §9 приоритеты и дорожная карта → §10 что не менять.

Оценки трудоёмкости: **S** — 1–3 сессии, **M** — 1–2 недели сессий,
**L** — 3+ недели. Это порядок величины для планирования, не смета.

## 1. Диагноз

### 1.1. Что уже есть и работает (это много)

Конвейер «найти → обогатить → верифицировать → разослать ведомость →
принять ответ → распознать счёт → сопоставить со сметой → сравнить → отобрать
→ согласовать» существует целиком и прошёл живую эксплуатацию. Ключевые
работающие узлы:

- каталог на 1141 карточку поставщика в 24 категориях закупки, 114 товарных
  групп по снимкам сайтов, 8 хабов × 27 плиток «как у ВсеИнструменты»
  (`src/components/suppliers/SupplierCatalog.tsx`, `src/data/supplierCatalog.ts`);
- очереди в Supabase Edge Functions (`process-supplier-jobs`,
  `process-bulk-send-jobs`, `process-outgoing-emails`) с атомарным захватом,
  бэкоффом и идемпотентностью одиночных писем;
- массовая рассылка с персонализацией, антиспам-темпом и трёхслойным дедупом
  (`supabase/functions/process-bulk-send-jobs/index.ts`);
- приём ответов вебхуком Resend, автораспознавание счетов на Haiku 4.5
  (~$0,005 за документ) и автозапись в карточку с точечным откатом
  (`api/_invoiceRecognition.js`, `api/_invoiceApply.js`);
- автоответы поставщикам по 13 ситуациям с обучением на разборе с владельцем
  (`docs/auto-reply-routine.md`);
- сравнение цен по позициям ведомости, ручной отбор, лист согласования, PDF,
  ИИ-подсказка сопоставления (`src/components/suppliers/PriceComparisonCard.tsx`);
- проверка благонадёжности по ИНН через Checko (`api/_checko.js`),
  слияние дублей (`src/lib/supplierMergeApi.ts`);
- «ИИ-закупщик» как видимый сотрудник с живым статусом и метриками — готовая
  продуктовая метафора.

### 1.3. Чем текущая система отличается от продукта

1. **Половина конвейера живёт вне прода.** Робот съёма сайтов — Playwright в
   Chrome на Mac владельца (`scripts/harvest.mjs`); классификация сайтов по
   товарным группам — субагенты сессии Claude Code с ручной сверкой
   (`scripts/supply-categories/review.mjs`, `LESSONS.md`); автоответы —
   почасовая Routine на Opus в аккаунте владельца, не код репозитория
   (`src/data/emailAutoReply.ts:1-20`); разбор скриншотов каталога — тоже
   сессия. Для одной компании это гениально дёшево, для продукта —
   невоспроизводимо: у клиента нет ни Mac владельца, ни подписки Max x20.
2. **Точка входа в поиск поставщиков удалена из UI** (коммит `496421f`,
   `queueSupplierWebSearch` — мёртвый экспорт). База «закрыта» решением от
   2026-09-15 — для своих нужд достаточно, для клиента из Казани или Минска с
   другим ассортиментом база пуста.
3. **Цикл обрывается на «Утверждено».** Ни заказа, ни оплаты, ни доставки,
   ни приёмки, ни документов поставки — `purchases` и `supplier_orders`
   пусты, статусы «Заказано / Оплачено / Доставлено» лежат в отключённой
   сущности `Purchase` (`src/data/purchases.ts:8`, `src/pages/Purchases.tsx`
   вне роутера).
4. **Поставщик — не сущность, а «предложение в категории»**
   (`supplier_research_offers`): одна компания = несколько карточек, ИНН
   появляется только после первого счёта, слияние дублей привязано к
   удалённому понятию «универсальные поставщики»
   (`src/pages/Suppliers.tsx:2140`).
5. **Всё жёстко под одну компанию:** домен `zakupki+…@redevelopment.pro`
   в трёх местах, имя отправителя «Анатолий Трэшмен» в трёх файлах, страны
   ровно две, валюты три, реестр только Checko/Россия, категории каталога в
   коде, смета по умолчанию — объект `one`, адрес доставки — в тексте
   ситуаций автоответа.
6. **Инфраструктурные потолки уже искажают архитектуру:** Vercel Hobby —
   12 функций (четыре инцидента, готовая белорусская проверка
   `api/_belarus.js` не подключена из-за него), Supabase free-tier (квота
   организации превышена, Max rows 1000 уже режет выборки снимков меню),
   Resend free (100 писем/сутки — упирались 2026-09-12).

## 2. Обещание 1: «запросить цены со всего рынка в пару кликов»

Сейчас «пара кликов» — это: создать запрос → вкладка «Письма» → модалка
рассылки → выбрать категорию, юрлицо, страну, фильтр адресатов, ведомость,
шаблон → очередь. Адресаты подбираются вручную, рынок = 1141 карточка одной
компании, ответ приходит произвольным PDF, молчание никак не обрабатывается.

### 2.1. Мастер «Новая закупка» в три шага — **M**

Один экран вместо пяти вкладок: **(1) что нужно** — раздел сметы, готовая
ведомость, вставленный список или xlsx; **(2) кому** — автоподбор адресатов
(см. 2.2) с показом покрытия «42 поставщика, 38 с email, 3 в чёрном
списке»; **(3) условия и отправка** — регион поставки, срок ответа (SLA),
режим сравнения `lot/material`, шаблон, юрлицо. Кнопка «Запросить цены».
Дальше всё делает ИИ-закупщик, человек возвращается к готовой таблице.
Сейчас `SupplierRequest` создаётся, но нигде не отображается и не правится
(`Suppliers.tsx:2289`, `:2739` — ветка редактирования мертва).

### 2.2. Автоподбор адресатов по товарным группам и региону — **S/M**

Каталог уже знает, кто что возит (`supplier_site_snapshots.categories`), но
рассылка идёт по «домашней» строке категории, а не по группам
(`BulkSendModal.tsx:638`). Нужно: адресаты = поставщики, у которых есть
группы позиций ведомости ∩ регион ∩ не в стоп-листе ∩ не «bounce» ∩ рейтинг
≥ порога; отдельно «уже отвечали по этой группе раньше — в приоритет».
Плюс ручная докрутка чипами. Это превращает 114 групп из навигации в
маршрутизацию.

### 2.3. Структурированный канал ответа для поставщика (портал КП) — **M**

Самый большой рычаг по конверсии «ответил → КП». В письме — ссылка вида
`/quote/<token>` (паттерн `/plan/:token` и OTP-подписание уже есть в репо):
поставщик видит ведомость, ставит цену, наличие, срок, минимальную партию,
условия доставки, прикладывает счёт, отмечает аналог с пояснением. Ответ
попадает в базу структурированным, без распознавания. Те, кто всё равно
ответит PDF, идут старым путём. Заодно поставщик может править свои контакты
и профиль — база чистится сама.

### 2.4. Дожим: SLA, напоминания, состояния «отказ» и «нет ответа» — **S/M**

Сегодня статус «Отправили, ждём ответ» висит вечно
(`offerCommunicationStatus`, `supplierResearch.ts:450`), напоминаний нет ни
в коде, ни в кроне. Нужно: срок ответа у закупки; напоминание через N дней и
второе через M (шаблоны, отправляет ИИ-закупщик); автоматическое «нет
ответа» и «отказ» как явные состояния (сейчас отказ существует только как
эвристика в промпте Routine №2); воронка показывает «дожимаем 12».

### 2.5. Обработка bounce / delivered / opened — **S**

Вебхук не смотрит `payload.type` (`purchase-email-webhook.js:344`), мёртвый
адрес будет получать письма вечно. Подписаться на события Resend, помечать
email как невалидный, снимать с рассылки, писать в рейтинг поставщика,
показывать «доставлено/открыто» в треде.

### 2.6. Цены из тела письма и «цена по запросу» — **S/M**

Распознавание запускается только по вложениям
(`purchase-email-webhook.js:475`); цены в тексте письма и ответы «пришлите
объёмы — назовём цену» в базу не попадают. Добавить извлечение цен из текста
(та же модель), ситуацию «цена по запросу» в автоответы (автоматически
досылать ведомость/объёмы), снять потолок в 3 страницы PDF через разбиение
(`_invoiceRecognition.js:29`), ввести числовой confidence вместо бинарного
`isInvoice` — по нему решать «записать сразу / показать человеку».

### 2.7. Матчинг ответов не только по plus-адресу — **S**

Единственный ключ — `zakupki+<code>@` (`purchase-email-webhook.js:122`);
письмо «в новом окне» на голый `zakupki@` теряется молча (`:359-366`), ключ
уже разъезжался в проде (фолбэк `resolveOfferIdByEmailHistory`). Добавить
`In-Reply-To`/`References`/`Message-ID` (Resend их отдаёт) и адрес
отправителя; неразобранное — в очередь «Разобрать вручную», а не в
`skipped`.

### 2.8. Мультиканальность: Telegram, WhatsApp, Max, телефон — **M/L**

Мессенджеры собраны у 611 карточек, но отправки по ним нет ни строчки.
Этап 1 — «написать в мессенджер» с готовым текстом и логированием исхода;
этап 2 — Telegram Bot API и WhatsApp Business API для реальных диалогов в
том же треде; телефон — фиксация звонка с транскрибацией через уже
существующий `api/transcribe.js` и извлечением цены/условий из разговора.

### 2.9. Поиск поставщиков как воспроизводимая функция продукта — **L**

Вернуть «Найти поставщиков по категории в регионе», но не как ~195 ₽ за
задание LLM-поиска, а конвейером: (а) структурные источники — API 2ГИС /
Яндекс.Карты, выгрузки ЕГРЮЛ/ЕГР по ОКВЭД, отраслевые каталоги, импорт
списков клиента; (б) снимок сайта без модели (уже есть в Edge Function);
(в) классификация с «уликой» — автоматизированная в Edge Function по
протоколу 97 % из `LESSONS.md`, не сессией; (г) съём меню и контактов —
облачный headless-браузер с резидентными прокси вместо Mac владельца;
(д) кэш «категория × регион» общий для всех клиентов — второй клиент по
керамограниту в Москве получает готовых поставщиков бесплатно.

### 2.10. Общая база поставщиков как сетевой актив — **L** (стратегическое)

Разделить данные на два слоя: **глобальный реестр компаний** (домен, ИНН,
сайт, ассортимент, регион, публичные контакты, реестровая проверка) и
**приватные отношения клиента** (переписка, цены, рейтинг, менеджеры,
стоп-лист). Каждый клиент пополняет покрытие и бенчмарк цен, не раскрывая
своих КП. Это и есть защищаемое преимущество перед тендерными площадками, у
которых базу набирают сами поставщики.

### 2.11. Аренда чужой сети поставщиков — **M**

Сетевой эффект площадок (Закупай — 5 000 поставщиков, Supl.biz — 1,47 млн,
1С:Бизнес-сеть — все, у кого 1С) в одиночку не повторить, но его можно
арендовать: публиковать заявку параллельно на площадки и собирать ответы к
себе тем же вебхуком/порталом. Клиент получает охват площадок и нашу
нормализованную таблицу вместо их «кучи счетов».

## 3. Обещание 2: «быстро и автоматически сравнить цены»

Сравнение перестроено 2026-09-15 и стало правильным по модели (единица —
позиция ведомости), но «автоматически» пока не выполняется: таблица пуста,
пока человек не сопоставит строки счёта с позициями.

### 3.1. Автосопоставление при приёме счёта — **S**

`api/_proposalMatches.js` (Sonnet 5 с фолбэком на Haiku) вызывается только
по кнопке и требует построчного подтверждения (`PriceComparisonCard.tsx:383`,
`:438`). Запускать его сразу в `_invoiceApply.js`, сохранять `sourceMaterialId`,
`unitPrice`, `matchKind` с confidence; человеку показывать только строки
`check` и низкую уверенность. Таблица заполняется к моменту открытия.

### 3.2. Справочник единиц, тары и НДС как данные — **M**

Нормализация покрывает м²/м³/шт (`src/lib/units.ts:5-15`), пересчёт тары
работает только при заполненном `consumption` и объёме в названии
(`src/lib/unitPriceGuess.ts:57-66`), НДС — кнопка «×1,22» и текст «с НДС».
Нужно: словарь единиц с синонимами (пог.м, п.м., уп, рул, пач, мешок) и
коэффициентами; кратность упаковки и минимальная партия; поле «цена без
НДС / ставка» у строки и у КП; страновые ставки (20 % РФ, 20 % РБ, 12 % KZ).

### 3.3. Условия как структурированные поля — **M**

Сейчас условия — свободный текст `termsNote`, доставка ловится регуляркой по
названию строки (`purchases.ts:87`). Извлекать моделью из писем и счетов в
`quote.terms`: стоимость и условия доставки, срок поставки (дней), наличие
(в наличии / под заказ), предоплата %, срок действия КП, минимальный заказ.
В таблице — колонки/чипы условий; итог «цена + доставка» и «срок» рядом.

### 3.4. Режим рекомендации ИИ при сохранении ручного отбора — **S/M**

Владелец сознательно убрал минимум цены («считает по аналогам, которые не
подойдут»). Оставить ручной отбор по умолчанию, но дать кнопку
«Предложить отбор»: только `exact`, с учётом срока/доставки/рейтинга, с
объяснением по каждой позиции. Для `comparisonMode:'lot'` довести паритет —
отбор, лист согласования, PDF, воронка (сейчас lot остался на старом
`OfferTotalComparison`, `Suppliers.tsx:2461`).

### 3.5. История цен и бенчмарк рынка — **M**

Новый счёт вытесняет старый (`priceComparisonModel.ts`), прошлые закупки не
агрегируются, «протух 14 дней» — только бейдж. Нужно: таблица цен по
материалу × поставщик × дата; график в карточке поставщика и в сравнении;
подпись «на 12 % выше медианы рынка за 90 дней»; в перспективе — анонимный
кросс-клиентский индекс. Снимок согласования хранить числом с валютой и
датой курса, а не строкой (`supplierResearch.ts:249`).

### 3.6. Согласование как процесс с ролями — **M**

Сейчас адрес руководителя — свободный email в `localStorage`, «Утверждено»
жмёт сам закупщик, история решений не ведётся
(`PriceComparisonCard.tsx:105`, `:1257`). Нужно: роли закупщик / согласующий
/ утверждающий, лимиты по сумме, ссылка «Утвердить» с токеном (механика
OTP-подписания уже есть в `api/agreement-otp-*.js`), комментарии к строкам,
несколько раундов с журналом, уведомления в email/Telegram вместо
локального колокольчика.

### 3.7. Работа с аналогами и уточнениями из таблицы — **S**

Для строк `alternative`/`check` — извлекать моделью «чем отличается»
(бренд, коллекция, толщина) из письма и ссылки на товар; кнопка «Уточнить у
поставщика» прямо из ячейки формирует письмо через ИИ-закупщика.

### 3.8. Переторжка силами ИИ-закупщика — **S/M**

Стандарт ЭТП (Bidzaar, ГПБ) и то, что закупщик делает руками: после первой
таблицы попросить 2–3 лучших поставщиков улучшить цену/срок, назвав
обезличенный уровень конкурентов. Кнопка «Запросить лучшие условия» из
сравнения → письма от ИИ-закупщика → новые КП распознаются как вторая
волна и ложатся в ту же таблицу с пометкой «после переторжки».

### 3.9. Трассировка каждой цифры к исходнику — **S**

Как у BidLevel/Field Materials: клик по ячейке открывает счёт с подсветкой
строки, из которой взята цена (предпросмотр документа уже есть в переписке).
Доверие к автоматическому сравнению держится на этом.

## 4. Обещание 3: «организовать поставку/закупку»

После `review.status='approved'` перехода нет никуда — ни в заказ, ни в
деньги, ни в документы. Это самый большой пробел относительно обещания.

### 4.1. Сущность «Заказ» (PO) из утверждённого отбора — **M**

Один клик из утверждённого листа → заказы по поставщикам (группировка
отобранных ячеек), со статусами `ordered → invoiced → paid → shipped →
delivered → accepted → closed` (+ `cancelled`, `claim`). Взять дизайн
статусов из мёртвой `Purchase`, а сам мёртвый код (`Purchases.tsx`,
`purchasesApi.ts`, `purchase_emails`) удалить. `SupplierOrder` («доп.
заявка = ветка переписки») переименовать, чтобы не путать с заказом.

### 4.2. Отправка заказа поставщику и контроль финального счёта — **S/M**

Письмо-заказ со спецификацией (генерация из гугл-шаблона — механика
`api/generate-document.js` уже есть), запрос финального счёта; распознанный
финальный счёт сверяется с заказом — отклонения по цене/количеству
подсвечиваются до оплаты.

### 4.3. Оплата: связь с модулем «Транзакции» — **S/M**

В `src/data/transactions.ts` нет ни одного упоминания закупок. Из заказа
создавать плановый платёж (предоплата %, остаток), отмечать оплату, видеть
график платежей по объекту.

### 4.4. Логистика и приёмка — **M**

Дата и слот доставки, адрес из `legal_entities.delivery_info`, контакт на
объекте, частичные поставки; приёмка с телефона: фото, получено/заказано по
строкам, брак → претензия поставщику письмом через ИИ-закупщика. Отсюда же
считается «поставляет вовремя» в рейтинг.

### 4.5. Документы поставки — **S/M**

УПД / накладная / акт / сертификаты — распознаются тем же конвейером, что
счета, прикрепляются к заказу; чек-лист документов по заказу; выгрузка в
xlsx и в 1С (формат обмена — на этапе интеграций, §6.9).

### 4.6. Календарь поставок и дашборд закупок по объекту — **S/M**

Что заказано, что опаздывает, что оплатить сегодня, что приехало без
документов; уведомления в Telegram. Это «главная страница» продукта для
руководителя стройки.

### 4.7. Обратная связь в смету — **S/M**

`EstimateDetail.tsx` ничего не знает о закупках. Показывать у материала
статус (запрошено / есть КП / заказано / доставлено), факт против плана по
цене и экономию по закупке — это и есть главный KPI продукта.

## 6. Каркас продукта (чтобы это можно было продать не одному клиенту)

### 6.1. Модель арендатора — **L**

План от 2026-09-09 (`LICENSE_PROTOTYPE_PLAN.md` в ветке
`claude/modular-platform-client-sales-r6fgw4`) выбрал «никакой
мультитенантности, отдельный Supabase на клиента» как временную схему для
одного демо. Для продажи многим компаниям рекомендую наоборот: **одна база,
`organizations` + `org_members` + `org_id` на всех таблицах закупок, RLS по
claim в JWT, роли owner / buyer / approver / viewer**. Причина — §2.10:
общий реестр поставщиков и бенчмарк цен возможны только в одной базе.
Отдельный проект — как исключение для enterprise-клиента с требованием
изоляции. Существующая `access_profiles` (страницы по пользователю)
превращается в роли внутри организации.

### 6.2. Почта арендатора — **M**

Домен и имя отправителя вшиты (`purchase-send-email.js:37,66`,
`process-bulk-send-jobs/index.ts:28,48`, `process-outgoing-emails:32`;
подпись `'Трэшмен' → 'Анатолий Трэшмен'` в `SupplierCorrespondenceTab.tsx:558`).
Нужно: настройки организации (имя ИИ-закупщика и человека, подпись, юрлица,
адрес доставки); входящий поддомен на арендатора (`zakupki@<slug>.<домен
продукта>` через Resend Inbound) или собственный домен клиента с DKIM;
чек-лист SPF/DKIM/DMARC и прогрев в онбординге; `List-Unsubscribe` и текст
про обработку данных в первом письме; общий ящик → назначение
ответственного и `read_at` на пользователя (сейчас одна колонка на письмо).

### 6.3. Перенос «ручных» узлов внутрь продукта — **L**

Робот съёма → облачный headless-браузер (свой VPS с Playwright или
Browserless) с прокси и очередью; классификация сайтов → Edge Function с
моделью через API и правилом «улики», порог 97 % из `LESSONS.md` как
автотест; автоответы → серверная функция с моделью через API (Sonnet для
разбора, шаблоны — без модели), с тарификацией по арендатору; разбор
скриншотов → та же функция с vision-моделью. Букмарклеты оставить как
«инструмент продвинутого пользователя». Результат: продукт работает без
владельца в цепочке.

### 6.4. Снять инфраструктурные потолки — **S** (решение) / **M** (переезд)

Vercel Hobby 12 функций: перейти на Pro либо перенести `api/*` в Supabase
Edge Functions (там уже три очереди) с одним роутером. Supabase: платный
план с PITR (после инцидента CASCADE-удаления карточки с перепиской бэкапов
не было), Max rows → пагинация везде (`fetchAllSupplierOfferEmails` тянет
всё `select('*')` раз в минуту). Resend: платный план, лимиты по
арендатору. Без этого продавать нельзя — это первый пункт дорожной карты.

### 6.5. Страна и регион как настройки — **M**

Список стран с форматами телефонов, валютами (добавить KZT, UZS, EUR),
ставками НДС, реестрами (Checko — РФ; ГРП МНС + DaData `party_by` — РБ,
код готов в `api/_belarus.js` и не подключён; Казахстан — БИН через
stat.gov.kz), площадками для поиска, гео-подсказками по городам (сейчас
32 российских города в отсечке жёстко в `process-supplier-jobs`).

### 6.6. Таксономия арендатора и отраслевые пресеты — **M**

Хабы/плитки каталога — в БД, не в коде (`supplierCatalog.ts`), с пресетами:
«отделка офисов» (текущий), «жилое строительство» (бетон, арматура,
кладка, окна), «инженерные системы», «благоустройство»; товарные группы
уже в БД. Клиент выбирает пресет и правит.

### 6.7. Онбординг за 10 минут — **M**

Импорт ведомости/сметы из xlsx (Smeta.ru, ГрандСмета, простой список),
импорт своего списка поставщиков, подключение почты, выбор пресета, первая
закупка мастером §2.1 с готовыми поставщиками из общего реестра (§2.10).
Первая ценность — таблица сравнения — должна появиться в первый день.

### 6.8. Учёт стоимости и биллинг — **M**

Себестоимость LLM-заданий в БД не пишется вообще (только `usage` в консоль).
Считать стоимость каждого задания (поиск, распознавание, автоответ,
сопоставление) по арендатору; тариф — подписка за рабочие места + кредиты
на ИИ-операции / найденных поставщиков; лимиты плана (писем в сутки,
поисков в месяц). Внутри админки — «сколько ИИ-закупщик сэкономил и стоил».

### 6.9. Интеграции — **M/L**

1С (счета, УПД, контрагенты), Битрикс24 / amoCRM (контрагенты, сделки),
Telegram-бот (согласование, уведомления, «пришёл счёт»), xlsx экспорт/импорт
везде, публичный API и вебхуки для ERP клиентов.

### 6.10. Метрики арендатора — **S**

Страница «Метрики» уже считает работу ИИ-закупщика. Добавить продуктовые
KPI: экономия относительно первого КП и относительно медианы, цикл
закупки в днях, доля ответов, доля КП, доля закупок в срок, «ИИ сделал за
вас на этой неделе: 38 писем, 12 счетов, 4 напоминания».

### 6.11. Позиционирование — **S**

Герой продукта уже есть — «ИИ-закупщик»: сотрудник, который сам пишет
поставщикам, отвечает на их вопросы, собирает счета, строит сравнение и
приносит лист на подпись. Это отличается от тендерных площадок (там
поставщики приходят сами и торгуются) и от СРМ-подрядчиков (там нет
поиска и разбора почты). Модель цены — подписка + кредиты, поставщикам
бесплатно (портал §2.3).

## 7. Надёжность, безопасность, право

- **Подпись вебхука обязательна** — без `RESEND_WEBHOOK_SECRET` проверка
  молча пропускается (`purchase-email-webhook.js:335`), любой знающий URL
  подкинет письмо в переписку; сырой payload в логах — PII. **S**
- **Мягкое удаление и бэкапы** — карточка с перепиской уже удалялась
  CASCADE-ом (2026-09-11), восстанавливали из осиротевших вложений;
  soft-delete у поставщиков/писем/КП + PITR. **S/M**
- **Идемпотентность массовой рассылки** — `Idempotency-Key` есть у одиночных
  писем, нет у `process-bulk-send-jobs` (защита только индексом). **S**
- **Единый источник логики** — `renderTemplate`, `dedupKey`,
  `normalizePhone` продублированы в TS / Deno / .mjs с комментарием «менять
  синхронно»; вынести в общий пакет. **S/M**
- **Тесты точности** — «золотой» набор из 50 счетов и 50 писем поставщиков,
  прогон при каждой смене модели/промпта, дашборд точности; протокол 97 %
  из `LESSONS.md` как автотест классификации. **M**
- **Наблюдаемость** — очереди ошибок в UI (`supplier_harvest_failures`,
  `extraction.status='none'`, `outgoing_email_jobs.failed`), стоимость по
  заданию, алерты о простое агента (статус уже есть). **S**
- **Право на данные** — робот маскирует автоматизацию и обходит антибот
  (`harvest.mjs:196-199`), robots.txt не читается, персональные данные
  менеджеров хранятся без основания и срока; бакет скриншотов чужих сайтов
  публичный. Для продукта нужны: уважение robots.txt и rate-limit, политика
  обработки ПДн (152-ФЗ / закон РБ), согласие в первом письме, срок хранения,
  приватный бакет. Иначе первая же жалоба поставщика — риск для клиента. **M**
- **Управление сессиями Claude как частью процесса** — пока Routine и
  скрипты живут в аккаунте владельца, задокументировать это как временное и
  вынести (§6.3).

### 8.1. Сколько зарабатывает ближайший аналог (Checko, 2026-09-16)

Проверено по ИНН через Checko (годовая отчётность ФНС: выручка — строка 2110,
чистая прибыль — 2400). Обе компании — Санкт-Петербург, один генеральный
директор (Анисимов И. С.), то есть это одна группа: **ООО «Синтека»**
(ИНН 7813582855, cynteka.ru, 104 сотрудника) и **АО «Закупай»**
(ИНН 7811643020, zakupay.pro, 102 сотрудника). Суммы — млн ₽.

| Год | Синтека, выручка | Синтека, ЧП | Закупай, выручка | Закупай, ЧП |
|---|---|---|---|---|
| 2021 | 108,7 | 22,0 | 24,7 | 7,2 |
| 2022 | 172,1 | 57,3 | 135,9 | 18,4 |
| 2023 | 233,5 | 2,0 | 296,9 | 28,6 |
| 2024 | 338,8 | 0,9 | 358,3 | 26,2 |
| 2025 | 415,2 | 5,6 | 457,1 | 68,1 |

Итого по группе за 2025 — **872,3 млн ₽ выручки и 73,7 млн ₽ чистой прибыли**
(рост выручки с 2021 — в 6,5 раза). Рядом ещё два юрлица на том же бренде:
ООО «ТД „Закупай“» (выручка 2025 — 14,5 млн ₽) и ООО ТК «Закупай» (8,5 млн ₽),
по 1–2 сотрудника — похоже на торговые прокладки, в сумму выше не включены.

Что из этого следует для нас: ниша «снабжение для стройки как сервис» в РФ
кормит ~200 человек и даёт почти миллиард выручки на группу, то есть спрос
подтверждён деньгами, а не только нашими гипотезами. При этом прибыль сидит на
площадке («Закупай», рентабельность 14,9 %), а не на сервисе снабжения
(«Синтека» с 2023 года выводит прибыль почти в ноль: 2,0 → 0,9 → 5,6 млн ₽) —
внутри группы это чаще вопрос того, на какое юрлицо посажена маржа, чем разной
эффективности; ориентироваться на модель монетизации по одной рентабельности
нельзя.

**Норма 2026 (без этого не продукт):** заявка с объекта в клик, в т.ч. с
телефона; рассылка с трекингом «открыл/ответил» и авто-напоминаниями; ответ
поставщика без регистрации (ссылка / письмо / PDF); таблица side-by-side с
выбором построчно; отбор → заказ/счёт/PO → выгрузка в учёт (в РФ — 1С);
поставщику всегда бесплатно.

**Дифференциаторы, где мы уже впереди или можем быть:** ИИ-разбор писем и
счетов в строки с нормализацией (в РФ из коробки не делает никто);
автономный агент, который сам ведёт переписку (в стройке РФ/РБ отсутствует);
Telegram/WhatsApp/Max как канал ответа поставщика (свободная полка);
бенчмарк цен по истории; post-award с приёмкой и сверкой.

**Позиционирование:** не площадка и не ЭТП, а ИИ-закупщик поверх привычных
каналов (почта, мессенджеры, площадки) + нормализованная таблица + заказ и
поставка с выгрузкой в 1С. Ближайший по замыслу RU-аналог — связка
Синтека+Закупай — стоит от 46 тыс. ₽/мес и требует внедрения.

**Цена:** рабочая гипотеза — подписка с закупщика по объектам/объёму заявок
(ориентиры рынка: 10–50 тыс. ₽/мес в РФ, $149–599/мес на Западе) плюс
кредиты на ИИ-операции; поставщикам бесплатно навсегда; процента от GMV в
стройматериалах нет ни у кого — низкая маржа и уход в прямые сделки.

## 9. Приоритеты и дорожная карта

Принцип: сначала замкнуть цикл для себя (это же демо для первого клиента),
потом сделать воспроизводимым без владельца в цепочке, потом — рост.

### Этап 1 — замкнуть цикл и убрать заготовки (4–6 недель)

1. Компания как сущность + полноэкранная карточка с разделами (§5.2–5.3,
   5.5–5.7).
2. Автосопоставление при приёме счёта (§3.1), условия как данные (§3.3),
   трассировка цифры к исходнику (§3.9).
3. Дожим и состояния «нет ответа / отказ» (§2.4), bounce (§2.5), матчинг по
   заголовкам (§2.7), цены из тела письма (§2.6).
4. Заказ из отбора, статусы, письмо-заказ, связь с транзакциями (§4.1–4.3).
5. Мастер «Новая закупка» и автоподбор адресатов (§2.1–2.2).
6. Подпись вебхука, soft-delete, идемпотентность рассылки (§7).
7. Инфраструктура: Vercel Pro или Edge, платный Supabase с PITR (§6.4).

### Этап 2 — воспроизводимость и первый внешний клиент (6–8 недель)

8. Модель арендатора и роли (§6.1), почта арендатора (§6.2).
9. Перенос робота, классификации и автоответов внутрь продукта (§6.3).
10. Портал КП для поставщика (§2.3).
11. Таксономия и пресеты в БД (§6.6), страна как настройка (§6.5,
    подключить готовую проверку РБ).
12. Онбординг и импорт (§6.7), учёт стоимости (§6.8).
13. Приёмка, документы, календарь поставок, статус в смете (§4.4–4.7).

### Этап 3 — продукт и рост

14. Общий реестр поставщиков и бенчмарк цен (§2.10, §3.5).
15. Рейтинг поставщика (§5.4), режим рекомендации (§3.4), переторжка
    (§3.8), согласование с ролями (§3.6).
16. Мессенджеры и телефон (§2.8), поиск как функция продукта (§2.9).
17. Интеграции 1С / Telegram / API (§6.9), аренда чужой сети (§2.11),
    биллинг, метрики арендатора (§6.10).

## 10. Что не менять

- Очереди в Supabase, а не в GitHub Actions; атомарный захват заданий.
- Plus-адресация как основной ключ треда (добавить заголовки, не заменять).
- Автозапись счёта без кнопки «Подтвердить» с точечным откатом.
- Ручной отбор как режим по умолчанию в сравнении; рекомендация — опция.
- Правило «улики» при классификации сайтов и протокол точности 97 %.
- Правило «есть уточняющий вопрос — автоответ не отправляем».
- Персонализация и темп рассылки; единица работы — категория закупки.
- Снимки материалов в закупке (не живые ссылки) для уже созданных заказов;
  ведомости — живые.
