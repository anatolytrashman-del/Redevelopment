# Источники аналитики рынка (БЦ, офисы и вообще)

Копилка внешних источников рыночных данных, которые мы можем цитировать на публичных
страницах аналитики (`/minsk/analytics/*`), в гайдах и в питчах в СМИ. Пополняется по
мере находок; реализация (парсинг, занесение в `external_metrics`, вывод на страницу) —
отдельная работа, наличие источника в этом файле её НЕ означает.

Соседние файлы: `docs/sklady-sources.md` — уже разобранные источники по складам (там же
формат разбора «источник → что даёт → периметр»); `SEO_PLAN.md` — где эти данные
используются в SEO-контуре.

**Правила проекта, которые действуют на любой источник отсюда:**

- Фактом считается только **дословно процитированный текст** источника. Значение,
  снятое глазами с графика или диаграммы, не записывается никуда (так в 2026-09-08 был
  отклонён NAI Belarus). Если числа лежат в исходнике страницы как текст (JSON серии
  графика) — это текст, а не картинка, и цитировать их можно.
- Числа для публичных страниц живут в таблице `external_metrics`
  (`source` = ключ из `SOURCE_LABELS` в `src/data/marketSnapshots.ts`), не в коде.
- Атрибуция обязательна («по данным <источник>, <дата публикации>»). Легальность
  цитирования данных аналитики владелец подтвердил 2026-09-16 (см. `SEO_PLAN.md`).

## «Твоя столица» (t-s.by) — разбор 2026-09-16

Агентство недвижимости с многолетним собственным мониторингом. Корень раздела —
[`www.t-s.by/analytics/`](https://www.t-s.by/analytics/). Домен открыт из окружения
сессии обычным `curl`, страницы отдаются статическим HTML (Bitrix).

Что внутри:

| Страница | Что там |
| --- | --- |
| `/analytics/monitoring/comm_offer/bc_rent/` | **«Динамика ставок аренды офисов в БЦ Минска»** — линейный график, 4 ряда: класс A, B+, B, C, в **BYN за м²/мес**, 89 помесячных точек (фев 2018 — авг 2026) |
| `/analytics/monitoring/comm_offer/bc_sell/` | **«Динамика цен на продажу офисов в БЦ Минска»** — 2 ряда: класс B и класс C, в **USD за м²**, те же 89 точек |
| `/analytics/monitoring/bc.php` | «Классификация бизнес-центров, разработанная для г. Минска» — их методика отнесения БЦ к классам (текст, не числа) |
| `/analytics/monitoring/build/`, `/rent_price/`, `/cotteges_offer/` | жилая недвижимость и стройка — для нас периферия |
| `/analytics/issledovaniya-rynkov-nedvizhimosti/`, `/analytics/projects/`, `/analytics/zhilaya-nedvizhimost/` | исследования под заказ, проекты, обзоры жилого рынка |

**Главное техническое наблюдение:** числа графиков лежат прямо в HTML страницы как
JSON (amCharts, поле `dataProvider`), а не рисуются картинкой:

```
"dataProvider": [{"category":"фев 2018","column-1":"50.7","column-2":"33", ...}, ...]
"graphs": [{"title":"Класс A","valueField":"column-1"}, ...]
```

То есть это цитируемый текст источника, а не снятое с диаграммы значение — под правило
проекта подходит, и весь ряд с 2018 года снимается парсером в один заход. Достаточно
`curl` + разбор `dataProvider`/`graphs` (в исходнике кириллица в `\uXXXX`).

Оговорка самого источника, которую при цитировании надо переносить: «Ставки, указанные
на графике, являются справочными и основаны на предложениях собственников **с учётом
НДС**. Реальные ставки по заключенным сделкам могут быть ниже на величину до 10% в
зависимости от характеристик объекта… и текущей ситуации на рынке». То есть это **цены
предложения**, сопоставимые с нашим собственным сбором с Kufar/Realt, а не цены сделок.

Чем ценно для нас: это единственный найденный публичный ряд ставок **по классам БЦ и
помесячно на 8+ лет** — им закрывается то, чего наш собственный сбор дать не может
(история до начала нашего мониторинга и разрез по классу здания).

Что сделать, когда дойдут руки (не сделано):

1. Скрипт-парсер обеих страниц → `external_metrics`, ключ `source = tvoya-stolitsa-bc`
   (отдельно от складского `tvoya-stolitsa` — другой периметр и другая методика).
2. Ключ в `SOURCE_LABELS` (`src/data/marketSnapshots.ts`) с подписью «Твоя столица,
   мониторинг БЦ Минска» и обязательной оговоркой про НДС и цены предложения.
3. Решить периодичность обновления (у них ряд помесячный — хватит крона раз в месяц,
   не по часам, как синки спроса).

## Garantiruem.by и Pro-N.by — разбор и устройство (2026-09-20)

Оба подключены к городским сегментам (`citywide_offers`), сборщики —
`scripts/lib/citywideExtraSources.mjs` (`collectGarantiruemOffers`,
`collectProNOffers`). Полные технические комментарии — в самом файле у каждой
функции; здесь — что важно знать при следующей находке похожей площадки.

**Обе площадки режут обычный `fetch()` (Node/undici) по TLS/HTTP-отпечатку**, ещё до
любых заголовков — тот же запрос `curl`'ом проходит `200`, `fetch` с теми же
заголовками получает `403`. Обходной путь — звать системный `curl` из Node
(`execFile`), он есть и в песочнице, и на раннерах GitHub Actions без установки.
Domovita и Megapolis этим не страдают, их трогать не пришлось.

**Garantiruem — редкий случай, когда весь раздел отдаётся одним запросом.** Обе
страницы (`/lease/commerce/`, `/sale/commerce/`) кладут ВСЕ свои объекты в инлайн-
скрипт `new JCObjectMap([...])` — пагинация не нужна вовсе. Тип помещения в этом
массиве не передаётся (только на странице самого объявления, `<div class="obtt">`) —
для 190+28 объектов это означало отдельный GET на каждый ради типа, что и объясняет
самую большую своую долю (~80%): большинство объявлений реального агентства не
дублируется на порталы.

**Pro-N.by — у него нет ни одной страницы, до конца которой можно легально
долистать.** `robots.txt` разрешает страницу объявления (`/rent/nonres/<id>/`) кому
угодно, но `Disallow: /*?*` запрещает ЛЮБОЙ query-параметр — а вся пагинация листинга
живёт только через `?page=N&...`. Легальный обход, который публикует сам сайт —
`sitemap-objects.xml`: прямые URL без query, но общие на всю Беларусь (632 аренда +
708 продажи), Минск внутри не выделен — фильтруется после открытия каждой страницы.
Цена берётся НЕ из родного поля (BYN), а из встроенного в разметку JS-пересчёта
площадки же в доллары (`onclick="calc(this,'27&nbsp;$ за м²|24&nbsp;€...',...)"`) —
своя конвертация ценнее нашей, не тянет за собой зависимость от курса на дату.
Тип помещения — из `<div class="obtt">Офис</div>`; категория «Помещения» (263 из 404
лотов аренды, генерический тип самой площадки) сознательно не разносится ни в один
из трёх сегментов — не изобретаем классификацию, которой нет у источника.

Обе площадки требуют открыть КАЖДЫЙ объект отдельно (в отличие от Kufar/Realt/
Domovita/Megapolis, где одна страница листинга даёт разом 20–30 карточек) — у
Garantiruem это 218 запросов, у Pro-N — около 1340 (страна целиком). Прогон занимает
заметно дольше остальных источников: Garantiruem — 1–2 минуты на сегмент, Pro-N —
7–10 минут НА ВЕСЬ КРАУЛ (не на сегмент). Чтобы три скрипта сегментов (office/retail/
warehouse), вызванные подряд в одной сессии, не гоняли этот краул трижды, у Pro-N
есть файловый кэш на 3 часа (`loadDiskCache`/`saveDiskCache`, системный temp, не в
репозитории) — ускоряет только ручной прогон нескольких сегментов подряд, в
месячном кроне (разные GitHub Actions джобы, разные раннеры) не участвует и не
должен: у Garantiruem кэша нет вовсе (218 запросов дешевле, чем городить кэш).

**Две ошибки разбора, пойманные только на живом прогоне** (обе теперь в тесте нет —
специфика конкретных площадок, не общая логика): у Pro-N цена с разделителем тысяч
(`108&nbsp;817&nbsp;$`) не ловилась первой версией регулярки — резалась на первой
группе цифр, отдавая `null` вместо суммы (66 из 159 минских офисов в первом прогоне);
и у Garantiruem словарь типов был перепутан с Pro-N — там значения "Офис"/"Склад", у
Garantiruem — прилагательные "Офисное"/"Складское", из-за чего первый прогон дал 0
совпадений при полном наборе площадка⇄объектов, разобранных верно. Оба видны только
на реальных данных, не на синтетическом тесте, — держать в голове при следующей
похожей площадке: сверять словарь значений с ФАКТИЧЕСКИМ полем той конкретной
площадки, а не с похожим полем соседней.
