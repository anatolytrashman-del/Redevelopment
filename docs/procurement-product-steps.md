# Закупки как продукт — пошаговый план исполнения

Файл для работы «по одному шагу за диалог». Обоснование каждого шага — в
`docs/procurement-product-plan.md` (аудит от 2026-09-15, номера разделов
вида §2.4 ссылаются туда). Этот файл — только ЧТО делать, в каком порядке и
как понять, что шаг закрыт.

## Как пользоваться (для сессии, которая получила этот файл)

1. Прочитать `CLAUDE.md` целиком и этот файл. Найти первый шаг без `[x]`
   (или тот, что назвал владелец: «делай шаг 7»).
2. `git fetch origin && git status`; работать в ветке, которую назначил
   харнесс (см. системный промпт), не в `oodobu`.
3. Перед кодом: `grep -n` по `docs/session-journal.md` за последние 3–5 дней
   по теме шага — параллельные сессии могли уже что-то сделать.
4. Прочитать раздел плана, на который ссылается шаг, и файлы из блока
   «Где в коде». Не читать `Suppliers.tsx` (3500 строк) и
   `SupplierCorrespondenceTab.tsx` (2800 строк) целиком — только `grep -n` и
   диапазоны.
5. Сделать ровно шаг. Если шаг оказался больше одной сессии — разбить его на
   7a/7b прямо в этом файле, закрыть 7a, записать, что осталось.
6. Проверка: `npm run build:app` чистый; SQL-миграции — через Supabase
   Management API (см. CLAUDE.md), файл миграции — в `supabase/migrations/`,
   в конце `NOTIFY pgrst, 'reload schema';`; UI — мок-тест по правилам
   CLAUDE.md.
7. Публикация — сразу: PR в `oodobu`, merge, дождаться READY (правило
   владельца от 2026-09-14, повторно не спрашивать).
8. Отметить шаг `[x]` здесь, дописать строку в «Журнал выполнения» внизу
   этого файла и запись в `docs/session-journal.md`. Следующий шаг не
   начинать без команды владельца.

Размер шага: **S** — одна сессия, **M** — 2–3 сессии (разбивать по ходу).

## Ограничения, которые легко нарушить

- Vercel Hobby: ровно 12 файлов `api/*.js` без `_`-префикса. Новый эндпоинт
  = новый `action`/`kind` внутри существующего диспетчера
  (`api/purchase-send-email.js`, `api/supplier-web-search.js`,
  `api/trigger-rebuild.js`) или Supabase Edge Function. Пока шаг 0 не
  закрыт — тринадцатый файл ломает деплой молча.
- Supabase Max rows = 1000: любая новая выборка — с пагинацией или
  `.range()`.
- Миграции применяются раньше, чем код доедет до прода: только аддитивные
  (добавить колонку/таблицу можно; переименовать, удалить, ужесточить RLS —
  отдельным шагом после READY).
- Не трогать: очереди в Supabase (не GitHub Actions), plus-адресацию как
  основной ключ треда, автозапись счёта без кнопки «Подтвердить», ручной
  отбор в сравнении как режим по умолчанию, правило «есть уточняющий
  вопрос — автоответ не отправляем» (§10 плана).
- **Владелец не открывает письма руками.** Любое «положим в переписку и
  дождёмся подтверждения» — это не осторожность, а потерянные данные: никто
  не откроет. Распознали — записываем, а сомнение показываем там, куда
  смотрят: пометка «проверить» в сравнении цен, значок в карточке, строка в
  списке дел. Правило владельца от 2026-09-16 («записывай по умолчанию»),
  относится ко всем будущим шагам, а не только к распознаванию счетов.
- Ключи и токены не печатать и не коммитить.

   «появляются заказы со статусом `ordered`». Но письмо-заказ поставщику —
   шаг 12: в момент нажатия кнопки поставщик о заказе ещё ничего не знает, и
   статус «Заказано» был бы враньём ровно в том месте, ради которого
   заводится таблица. В `ordered` заказ переводит отправка письма (шаг 12)
   или человек руками, если договорился по телефону — статус меняется прямо
   в списке под листом согласования.
2. **Группировка по паре «поставщик + валюта», а не по поставщику.** У
   одного поставщика часть позиций может быть в долларах (так уже было у
   алюминия и оцинковки у Авангарда), а заказ с двумя валютами в одной
   сумме — это заказ, сумму которого нельзя назвать. Доставка ложится в тот
   заказ, валюта которого совпадает с валютой карточки: доставку поставщик
   считает в своей валюте, дробить её между заказами нечем.
3. **Номер заказа заводится в базе** (`next_purchase_order_number()`,
   «З-2026-0001»). В плане колонки `number` не было, но она нужна уже шагу
   12: в письме и в счёте заказ должен как-то называться, а uuid в письме
   поставщику — не название.
4. **Позиции заказа — тот же `PurchaseItem`**, что у ведомостей и счетов, а
   не новый тип: `quantity`/`unit` из ведомости, `price` — цена за единицу
   ведомости с НДС (та самая, по которой сравнивали), `sourceMaterialId`
   держит связь с позицией — по ней шаг 12 будет сверять счёт с заказом.
5. **Журнал заказа пишет триггер в базе, а не фронт.** Смена статуса может
   прийти из интерфейса, из Edge Function (шаг 12) или руками через SQL;
   если бы событие писал фронт, история молча зияла бы дырами ровно там, где
   она нужнее всего. Фронт пишет только `updated_by` — триггер переносит его
   в событие.
6. **Кнопку не запирали на «один раз».** Повторное нажатие спрашивает
   подтверждение и создаёт ещё заказы: часть позиций реально переигрывают на
   другого поставщика уже после утверждения. Лишний заказ удаляется мягко
   (`deleted_at`), потому что он мог быть уже оплачен.

**Грабли, на которые уже наступили (не повторять):**
- PostgREST отдаёт максимум 1000 строк: любая выборка, где строк может быть
  больше, — постранично. Так молча терялись 141 карточка и 393 снимка сайтов.
- `claude-sonnet-5` через ProxyAPI по умолчанию уходит в extended thinking и
  съедает весь лимит вывода: HTTP 200, `stop_reason: max_tokens`, пустой текст.
  Обязательно `thinking: {type: 'disabled'}`. Haiku этим не страдает.
- `Number(String(v ?? ''))` превращает отсутствующее значение в 0. В условиях
  поставки это давало «доставка бесплатно, срок 0 дней» на письме «наберите
  меня».
- В `regexp_replace` с флагом `g` якорь `^` работает только на первое
  совпадение: `www.` после протокола не снимался, и один домен становился
  двумя компаниями.
- Пересчёт НДС нельзя делать при отрисовке сравнения: часть цен в базе уже
  пересчитана руками, и налог лёг бы вторым слоем. Место пересчёта — момент
  сопоставления, а сравнение только помечает.
- Молчание документа — не ответ «нет». Счёт, ничего не сказавший про НДС, не
  считается счётом без НДС; письмо без условий не обнуляет условия, названные
  раньше. Тот же класс ошибки, что `Number(String(v ?? ''))` → 0. Молчание
  ПОСТАВЩИКА, в отличие от документа, ответом «нет» в итоге становится — но
  только после двух напоминаний и трёх сроков ожидания, а не само по себе.
- Идентификатор письма у Resend и заголовок `Message-ID`, который видит
  получатель, — РАЗНЫЕ значения (uuid от `POST /emails` против
  `<…@eu-west-1.amazonses.com>` от SES). Ответ поставщика ссылается на
  второй. Проверять такие предположения на живом письме ДО того, как на них
  построен матчинг: план шага 9 был написан с неверным допущением.
- Вебхук был подписан на все типы событий Resend с 2026-08-29, но читал
  только входящие письма — отлупы «такого ящика не существует» полгода
  уходили в `{skipped:true}`. Подписка ≠ обработка; проверять
  `GET https://api.resend.com/webhooks` и то, что делает код с `payload.type`.
- `create or replace function` с ДРУГИМ числом аргументов не заменяет старую
  функцию, а заводит вторую. Дальше любой вызов со старым числом аргументов
  падает с «function is not unique». Добавляешь параметр — сначала
  `drop function` со старой сигнатурой (так сделано с `auto_reply_apply`).
- Service-role ключа в сессии нет, но он и не нужен: разовые прогоны по базе
  делаются через Management API (`SUPABASE_ACCESS_TOKEN`) плюс `PROXYAPI_KEY`
  для модели. Так выполнен бэкфилл сопоставления — владельцу ничего запускать
  не пришлось.
