## 0. Что просил владелец (дословно, чтобы не потерять смысл)

> 1. Добавляем подрядчика в ресерч либо автоматическим поиском, либо вручную
> 2. Далее находим контактный email, добавляем его в карточку подрядчика
> Нужно продумать отправку первого письма и как смотреть всю переписку.
> Точно нужна группировка по подрядчику, метка с категорией подрядчика
> (например "Умные замки", чтобы в памяти не держать), ну и сама группировка
> по этому тегу. Понадобятся шаблоны — письма для поставщиков замков будут
> похожими, но всё равно нужна возможность кастомно менять каждое письмо.

Решения, уже согласованные с владельцем в этой сессии (не переспрашивать):
- **Категория = сам запрос Ресерча** (`SupplierRequest.title`, например
  "Умные замки"). Отдельного поля "категория/тег" НЕ заводить — запрос уже
  группирует поставщиков, второе поле дублировало бы его. В интерфейсе
  переписки название запроса показывать бейджем на каждом треде.
- Порядок: сначала вкладка "Переписка" + шаблоны (этапы 2–3), рассылка
  пачкой — этап 4, отдельным коммитом.

### Этап 1 — Проверить формат входящего письма вживую (перед всем остальным)

- [x] **Подозрение подтверждено документацией (2026-09-03, поиском —
  resend.com недоступен из песочницы напрямую даже через WebFetch, только
  WebSearch-сниппеты).** `email.received` действительно несёт только
  метаданные (`email_id`/`from`/`to`/`subject`/`attachments`-список БЕЗ
  содержимого), дословно из документации: "Webhooks do not include the
  email body, headers, or attachments, only their metadata. You must call
  the Received emails API or the Attachments API to retrieve them."
  Тело: `GET https://api.resend.com/emails/receiving/{emailId}` →
  `{ text, html, headers, ... }`. Вложения — ОТДЕЛЬНЫЙ запрос (не тот же,
  что и тело): `GET https://api.resend.com/emails/receiving/{emailId}/attachments`
  → массив `{ id, filename, content_type, download_url (валиден 1ч), ... }`
  — сопоставляется с метаданными вебхука по `id`. Оба — `Authorization:
  Bearer RESEND_API_KEY` (уже есть в Vercel, новый секрет не нужен).
- [x] **Код исправлен** — `api/_attachments.js` (новый `fetchReceivedEmailBody`
  + переписанный `extractEmailAttachments`, теперь тянет `download_url`
  отдельным запросом вместо ожидания его в самом вебхуке) и
  `api/purchase-email-webhook.js` (`body` больше не читается из
  `data.text`/`data.html` — только через `fetchReceivedEmailBody`).
  Раньше КАЖДОЕ входящее письмо сохранялось бы с пустым `body` — это не
  крайний случай, а гарантированный баг на первом же реальном ответе.
  Синтаксис (`node --check`) и логика (сухой прогон с моком `fetch` —
  оба формата ответа: плоский и `{data:...}` SDK-обёрнутый, плюс полный
  путь вложения id→download_url→байты→загрузка в бакет) проверены в
  песочнице — реальный вызов `api.resend.com` из неё недоступен.
- [x] **Живой прогон проведён (2026-09-03) — и подтвердил, что формат
  ДЕЙСТВИТЕЛЬНО другой.** Владелец отправил письмо из карточки предложения,
  ответил с реальной почты, приложил файл. Входящая строка в
  `supplier_offer_emails` СОЗДАЛАСЬ (адресация/webhook в целом работают —
  подтверждено запросом к БД: `direction='in'`, верный `resend_message_id`),
  но `body_len=0` и `files=[]` — ровно тот баг, который этот этап должен
  был закрыть, всё ещё воспроизводится. Разбор `data.email_id`/`data.id`
  как id письма для Receiving API либо не то поле, либо сам `RESEND_API_KEY`
  не имеет прав на Receiving API (Resend различает уровни "Sending access"
  и "Full access" — ключ создавался только под отправку).
- [x] **Причина №1 (тело письма) подтверждена и устранена (2026-09-03).**
  Ключ `RESEND_API_KEY` в Vercel указывал на ключ Resend с правами только
  "Sending access" (второй ключ, `redevelopment-site`, с "Full access",
  висел неиспользуемым — "No activity"). Владелец поменял права
  существующего ключа через Resend Dashboard → API Keys → "..." → Edit
  API key (значение ключа при этом не меняется — на Vercel ничего не
  трогали, редеплой не понадобился). Повторный живой тест: `body_len`
  0 → 477, текст письма читается в ленте. Диагностика (несколько
  id-кандидатов, логирование сырого payload) себя оправдала — оставлена в
  коде, штатное поведение (пробует `email_id`, потом `id`).
- [ ] **Причина №2 (вложения) — ОТДЕЛЬНАЯ, ещё не закрыта.** Тот же
  повторный тест: тело пришло, файл — нет (`files=[]`). Раз тело успешно
  получено через тот же Receiving API с теми же (уже полными) правами,
  проблема не в доступе, а скорее всего в том, что `data.attachments` в
  самих метаданных вебхука для этого письма был пуст или назывался иначе —
  `extractEmailAttachments` в этом случае даже не делает запрос за
  `download_url`, сразу возвращает `[]` (см. `console.error` "пуст или
  отсутствует в вебхуке" в `api/_attachments.js`). Нужен вывод
  `RAW WEBHOOK PAYLOAD` из Vercel Runtime Logs за момент письма с
  вложением, чтобы увидеть реальную структуру `attachments`.

### Этап 4 — Рассылка первого письма всем поставщикам запроса ✅ ГОТОВО (2026-09-03)

**Владелец, 2026-09-03 (важно, читать перед началом): "учти момент, чтобы
мы не попали в спам за массовую отправку одинаковых писем. А то такое
ощущение, что если улетит 20 одинаковых писем одновременно, нас забанят,
домен новый".** Реальный риск, не перестраховка — домен `redevelopment.pro`
у Resend недавно верифицирован (DKIM/SPF/DMARC настроены 2026-09, живой
трафик почти не ходил), а у почтовых провайдеров (Gmail/Yandex/mail.ru и
т.п.) есть встроенная эвристика именно на "новый домен + пачка одинаковых
писем одновременно" — типичный паттерн спам-рассылки, даже если письма
абсолютно легитимны. Это НЕ про то, что Resend забанит аккаунт (у него
свои лимиты, см. ниже отдельно) — это про то, что письма реально попадут
в спам у получателей или домен получит плохую репутацию с самого начала,
до того как накопится история легитимной переписки. Учесть при
реализации:

- [x] **Персонализация — уже часть плана, не довесок.** Плейсхолдеры
  `{компания}`/`{материалы}`/`{запрос}`/`{контакт}` (этап 3) означают, что
  20 писем формально РАЗНЫЕ (разное приветствие, разный список позиций),
  не байт-в-байт идентичные — это уже сильно снижает риск именно
  спам-паттерна "identical bulk". Не срезать эту персонализацию ради
  простоты — не предлагать в модалке рассылки вариант "одно и то же всем
  без плейсхолдеров".
- [x] **Задержка между отправками**, не просто последовательность.
  Голый `for...of` с `await` всё равно шлёт письма настолько быстро,
  насколько успевает ответить сеть/Resend (может быть <1с между письмами)
  — выглядит как бот. Добавить явную паузу между отправками (`await new

## 4. Что НЕ делать

- Не заводить отдельную таблицу/поле "категория поставщика" — категория =
  запрос (решение владельца).
- Не создавать новые файлы в `api/` (лимит 12).
- Не переносить переписку в `purchase_emails` и не объединять таблицы —
  RFQ и оформленная закупка сознательно разделены (см. комментарий в
  `data/supplierOfferEmails.ts`).
- Не открывать `supplier_offer_emails`/`email_templates` для `anon` —
  только `authenticated`.
- Не рассылать через `Promise.all` И без задержки между письмами (см.
  этап 4 — оба требования, не одно вместо другого; последовательность
  сама по себе не защищает от паттерна "пачка одинаковых писем", если
  письма улетают друг за другом без паузы).
- Не предлагать в модалке рассылки (этап 4) вариант письма без
  плейсхолдеров "одно и то же всем" — персонализация обязательна, это
  часть защиты от спам-эвристик, не просто удобство.
