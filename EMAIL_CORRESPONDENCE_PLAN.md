# План: email-переписка с поставщиками в Ресерче (шаблоны, рассылка, входящие)

Инструкция для следующей сессии Claude Code (владелец, 2026-09-03: "напиши
инструкцию для себя же, я включу более простую модель для реализации").
Написана по итогам разбора кода в этой сессии — всё, что здесь названо
"уже есть", проверено по факту, а не по памяти. Читать ЦЕЛИКОМ перед
началом, потом идти по этапам по порядку, отмечая `[x]` в этом же файле.
В CLAUDE.md — только короткая запись в журнал по факту каждого этапа,
подробности не дублировать.

## 0. Что просил владелец (дословно, чтобы не потерять смысл)

> 1. Добавляем подрядчика в ресерч либо автоматическим поиском, либо вручную
> 2. Далее находим контактный email, добавляем его в карточку подрядчика
> Нужно продумать отправку первого письма и как смотреть всю переписку.
> Точно нужна группировка по подрядчику, метка с категорией подрядчика
> (например "Умные замки", чтобы в памяти не держать), ну и сама группировка
> по этому тегу. Понадобятся шаблоны — письма для поставщиков замков будут
> похожими, но всё равно нужна возможность кастомно менять каждое письмо.

Решения, уже согласованные с владельцем в этой сессии (не переспрашивать):
- **Категория = сам запрос Ресерча** (`SupplierRequest.title`, например
  "Умные замки"). Отдельного поля "категория/тег" НЕ заводить — запрос уже
  группирует поставщиков, второе поле дублировало бы его. В интерфейсе
  переписки название запроса показывать бейджем на каждом треде.
- Порядок: сначала вкладка "Переписка" + шаблоны (этапы 2–3), рассылка
  пачкой — этап 4, отдельным коммитом.

Схема `supplier_offer_emails` (проверена через Management API):
`id uuid`, `offer_id uuid NOT NULL`, `direction text NOT NULL` ('in'|'out'),
`from_address text NOT NULL`, `to_address text NOT NULL`,
`subject text NOT NULL DEFAULT ''`, `body text NOT NULL DEFAULT ''`,
`files jsonb NOT NULL DEFAULT '[]'`, `resend_message_id text NULL`,
`created_at timestamptz`. **Колонки `read_at` пока НЕТ** — см. этап 2.

Инфраструктура Resend на стороне владельца: домен верифицирован (DKIM/SPF/
MX на приём — Verified), тумблеры Sending/Receiving включены, вебхук на
`/api/purchase-email-webhook` заведён, `RESEND_WEBHOOK_SECRET` в Vercel
есть (с 29 августа). Т.е. со стороны кабинета всё готово.

## 2. Ограничения проекта, которые ЛЕГКО нарушить (читать обязательно)

- **Vercel Hobby: максимум 12 serverless-функций** (`api/*.js` без `_` в
  начале). Сейчас ровно 12. **Ни одного нового файла в `api/` заводить
  нельзя** — всё новое (шаблоны, рассылка) встраивать в
  `purchase-send-email.js` через дополнительные поля тела запроса.
- **SQL-миграции выполняем сами** через Supabase Management API (см.
  CLAUDE.md, раздел "SQL-миграции", `$SUPABASE_ACCESS_TOKEN`), в конце
  каждой DDL — `NOTIFY pgrst, 'reload schema';`. RLS на новые приватные
  таблицы — политика `authenticated_all` для роли `authenticated` (НЕ
  `anon` — это устаревший паттерн из старых записей журнала).
- **NOT NULL-ловушка**: у текстовых колонок в этом проекте почти всегда
  `NOT NULL DEFAULT ''`. Из клиента слать пустую строку как есть, НЕ
  приводить к `null` через `|| null` — ровно на этом в этой сессии упал
  `insertPledge` ("violates not-null constraint"). Перед написанием
  insert/update **сверить схему таблицы запросом к
  `information_schema.columns`**, не по памяти.
- Перед коммитом: `npx tsc -b && npx vite build`. Стейджить файлы
  поимённо, никогда `git add -A`. Перед началом работы `git fetch origin
  claude/redevelopment-platform-prototype-oodobu` — параллельная SEO-сессия
  пушит в ту же ветку, конфликт почти всегда только в CLAUDE.md
  (сохранять обе записи).
- Мок-тест UI перед пушем: временный маршрут `/__test-suppliers` в
  `App.tsx` (бэкап файла в scratchpad, `diff` после отката должен быть
  пустым), Playwright `chromium.launch({ executablePath:
  '/opt/pw-browsers/chromium' })`, импорт из
  `/opt/node22/lib/node_modules/playwright/index.mjs`, перехват
  `**/rest/v1/**` и `**/api/**` через `page.route`. Ответ на `.single()`
  запрос — одиночный объект, не массив. Живой Supabase/Resend из
  песочницы не достать.

  хранятся в локальном стейте `overrides: Record<offerId, {subject,
  body}>`) → кнопка "Отправить N писем".

## 4. Что НЕ делать

- Не заводить отдельную таблицу/поле "категория поставщика" — категория =
  запрос (решение владельца).
- Не создавать новые файлы в `api/` (лимит 12).
- Не переносить переписку в `purchase_emails` и не объединять таблицы —
  RFQ и оформленная закупка сознательно разделены (см. комментарий в
  `data/supplierOfferEmails.ts`).
- Не открывать `supplier_offer_emails`/`email_templates` для `anon` —
  только `authenticated`.
- Не рассылать через `Promise.all`.
