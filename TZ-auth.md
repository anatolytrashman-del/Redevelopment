## 1. Что услышал

Анатолий — владелец платформы redevelopment; первый клиент — ООО «Матрёшка», админка клиента на `основа.redevelopment.pro` (латинский алиас `osnova.redevelopment.pro` тоже подключён и работает).

Своими словами запрос:
- **Сейчас:** рабочий вход по **email + пароль** (пароли выдаёт Анатолий) для Анатолия и Грузева + заготовка под Битрикс24. Это рабочий способ входа, не аварийный.
- **Срок:** в понедельник Грузев входит в платформу. **Битрикс24 подключаем позже**, когда дадут приложение.
- Без списка сотрудников в коде; доступ получают только те, кого добавил владелец; это фундамент для блоков 2–4.
- **Заготовка:** слой «провайдер авторизации», куда позже подключается Битрикс24 (SSO) без переделки остального.
- **Позже (при подключении Битрикс24):** сотрудники клиента входят кнопкой «Войти через Битрикс24», профиль импортируется к нам; вход по email + пароль остаётся.
- У Анатолия два независимых доступа: владелец в админке платформы и **обычный пользователь** в Матрёшке — без пометки и прав владельца.

### 1.1. Что сейчас и почему плохо

| Что есть | Почему плохо |
|---|---|
| `PasswordGate.tsx`: выбор имени из списка + общий пароль, внутри Supabase Auth | Отдельные пароли, которые надо раздавать и помнить |
| Список сотрудников захардкожен в `src/data/loginAccounts.ts` | Имена и логины **видны любому** в JS-бандле; каждый новый сотрудник = релиз |

| Аккаунты заводятся вручную через Supabase Management API | Нет интерфейса, нет контроля |
| `access_profiles` — один общий набор доступов на платформу | Нет понятия «клиент», нельзя дать клиенту свою админку |
| `api/_auth.js` проверяет только «есть сессия» | Нет проверки роли и клиента на сервере |
| Нет журнала входов, нет отзыва доступа | Уволенного нельзя быстро и проверяемо отключить |

## 2. Ограничения и требования

### 2.1. Сроки и процесс
- **Жёсткий срок:** в понедельник Грузев входит по email + паролю.
- Прод-ветка — `claude/redevelopment-platform-prototype-oodobu` (далее `oodobu`); все изменения мёржатся в `oodobu`.
- Автодеплой Vercel из git выключен: прод выкатывается вручную через Vercel CLI, только после «да» Анатолия; сначала превью.

### 2.2. Принятые решения
- Аккаунты **создаёт только владелец**, саморегистрации нет.
- Двухфакторки нет. Сессии **бессрочные**, но отзываемые.
- Роли хранятся в базе (не в коде и не в localStorage), на двух независимых уровнях — платформа и клиент.

### 2.3. Безопасность (нефункциональные требования)
- Пароли — только хэш (средствами Supabase Auth); в коде, логах и переписке в репозитории паролей нет. Минимум 10 символов. Пароль Грузеву Анатолий передаёт сам.
- **Защита от перебора паролей:** вход по email + пароль — 5 неудачных попыток на email / 15 мин → блок на 15 мин + лимит по IP; для `api/auth/*` (в т.ч. будущего Битрикс24) лимит на `api/auth/bitrix/*` — 20 запросов / 15 мин с IP; неверный/просроченный `state` → отказ и запись в журнал; 10 отказов подряд с IP → блок на 15 мин.
- `client_secret` Битрикс24 и `service_role` Supabase — только в env Vercel / на сервере; в бандле и репозитории их нет.
- Только HTTPS; redirect URI — строго совпадающий, без открытых редиректов.
- Отключённый пользователь теряет доступ к `api/*` не позже чем через 1 мин.
- Раз в сутки (или при входе) — проверка `ACTIVE` в Битрикс24; уволенный там → «Отключён» у нас.
- Журнал безопасности: вход (успех/отказ, причина), добавление/отключение сотрудника, смена роли, синхронизация профиля — кто, когда, IP.
- Убрать захардкоженные списки пользователей и fallback-ключи из кода.
- Публичные страницы по токенам (`/plan/:token`, `/tz/:token`, `/estimate/:token`, `/summary/:token`, `/favorites/:id`) работают **без входа**, как сейчас.
- Работает на Vercel-проде из РФ и РБ.

### 2.4. Границы блока (что НЕ входит)
- ❌ Интерфейс админки клиента, детальные права ролей — **блок 2**.
- ❌ RLS-изоляция данных по `client_id`, общая база поставщиков — **блок 3**.
- ❌ Перенос данных Матрёшки — **блок 4** (в блоке 1 — только подключение портала и тестовые входы).
- ❌ Саморегистрация, вход по телефону, 2FA, восстановление пароля «по почте» самим сотрудником (пароль сбрасывает Анатолий).
- ❌ **Реальная интеграция с Битрикс24** (создание приложения в портале, подключение, вход сотрудников) — отложено, делается позже по готовой заготовке.
- ❌ Заведение остальных сотрудников Матрёшки (Зуев и др.) — позже; сейчас только Анатолий и Грузев.
- ❌ Двусторонняя синхронизация с Битрикс24 (мы только читаем профили, ничего туда не пишем).
- ❌ Ограничение срока жизни сессий.

## 3. Что будет сделано и как проверю

### 3.1. Целевое состояние

```
АДМИНКА ПЛАТФОРМЫ (отдельный контур)
└── Владелец платформы — Анатолий: видит всех клиентов       ← СЕЙЧАС

АДМИНКА КЛИЕНТА (у каждого клиента своя), напр. ООО «Матрёшка»
│   (+ портал Битрикс24 — ПОЗЖЕ)
├── Анатолий — обычный пользователь клиента (НЕ владелец)    ← СЕЙЧАС
├── Администратор клиента (М. Зуев)                          ← ПОЗЖЕ
├── А. Грузев — сотрудник, «Закупщик»                         ← СЕЙЧАС (понедельник)
└── Остальные сотрудники                                      ← ПОЗЖЕ
```

**Сейчас (этап 1)**
- Вход для всех — **email + пароль**, пароль выдаёт Анатолий.
- Активные пользователи: **Анатолий** и **Грузев**.
- У Анатолия **два независимых доступа**:
  - в админке платформы — роль `platform_owner` (видит всех клиентов);
  - в Матрёшке — обычное членство `client_staff`, как у любого сотрудника клиента; роль владельца платформы там **не видна и не действует**.
- Грузев — членство в Матрёшке, роль `client_staff`, должность «Закупщик»; видит админку Матрёшки как закупщик.
- Зуев и остальные сотрудники Матрёшки — **позже**.
- Архитектура: интерфейс провайдера авторизации + конфиг портала клиента + скрытая кнопка входа Битрикс24.

**Позже (этап 2, после согласования Битрикс24) — флоу входа**
```
[Войти через Битрикс24] → портал клиента (OAuth 2.0)
   → api/auth/bitrix/callback: проверка state, обмен кода на токен
   → профиль (user.current) → есть ли в «разрешённых»?
        нет → «Доступ не выдан»
        да  → импорт/обновление профиля → наша сессия → в приложение
```

### 3.2. Провайдер авторизации (заготовка — делаем сейчас)
- Единый серверный интерфейс провайдера: `начать вход` → `обработать ответ` → `получить профиль` → `создать сессию`.
- Реализации: **`password`** (email + пароль) — рабочая, для всех пользователей; **`bitrix24`** — заглушка, возвращает «Провайдер не подключён».
- Включение провайдера — флагом в конфиге (по умолчанию `bitrix24 = выключен`). Кнопка «Войти через Битрикс24» при выключенном флаге **скрыта**.
- Конфиг портала клиента (таблица/карточка клиента): адрес портала, `client_id`, ссылка на секрет, флаг `enabled`. Сейчас поля есть, но **пустые**; секретов в репозитории нет.
- Redirect URI (на будущее): `https://<домен платформы>/api/auth/bitrix/callback` — маршрут заведён, при выключенном провайдере отвечает 404/«не подключён».

### 3.3. Вход по email + пароль и профили (делаем сейчас, к понедельнику)
- Экран входа: «Email» + «Пароль» + «Войти». Без списка имён. Ошибка общая: «Неверный email или пароль».
- Аккаунт создаёт **только Анатолий** (в админке платформы): ФИО, email, клиент, роль, должность → задаёт пароль и передаёт его сотруднику сам.
- Анатолий может сменить/сбросить пароль сотрудника и отключить его; сотрудник может сменить свой пароль в профиле (с вводом текущего).
- Профили, которые заводим сейчас:

| Пользователь | Админка платформы | Матрёшка |
|---|---|---|
| Анатолий | `platform_owner` | `client_staff` (обычный пользователь, без пометки владельца) |
| Андрей Грузев | — (нет доступа) | `client_staff`, должность «Закупщик» |

- Внутри админки Матрёшки Анатолий отображается как обычный пользователь: без бейджа «владелец платформы», без лишних прав.
- Зуев и остальные — позже. Старые захардкоженные аккаунты отключаются.
- При подключении Битрикс24 аккаунт Грузева привязывается к его профилю Битрикс24 по email (без нового аккаунта).

### 3.4. Добавление сотрудников и вход через Битрикс24 (ПОЗЖЕ, при подключении)
- Владелец добавляет сотрудника в клиента: email или ID пользователя Битрикс24 + роль; опция «подтянуть список из портала» с отметкой галочками.
- Вход — OAuth 2.0 authorization code с одноразовым `state` (10 мин).
- Сопоставление: (портал + ID Битрикс24), при первом входе — по email.
- Не добавленный владельцем → «Доступ не выдан», аккаунт не создаётся. `ACTIVE = false` в Битрикс24 или «Отключён» у нас → вход запрещён.

### 3.5. Импорт профиля Битрикс24 → платформа (ПОЗЖЕ; модель данных — сейчас)
Поля таблицы профиля заводим сейчас; заполняются при подключении Битрикс24. Импорт при каждом входе + по кнопке «Обновить из Битрикс24». Данные **хранятся у нас**.

| Битрикс24 (`user.current` / `user.get`) | Наша платформа | Примечание |
|---|---|---|
| `ID` + адрес портала | `bitrix_user_id`, `bitrix_portal` | ключ сопоставления |
| `EMAIL` | `email` | |
| `NAME`, `LAST_NAME`, `SECOND_NAME` | `first_name`, `last_name`, `middle_name` | |
| `WORK_POSITION` | `position` | только справочно, **роль не задаёт** |
| `UF_DEPARTMENT` | `department` | названия через `department.get` |
| `PERSONAL_PHOTO` | `avatar_url` | копируем файл к себе (Supabase Storage) |
| `WORK_PHONE` / `PERSONAL_MOBILE` | `phone` | только контакт, не для входа |
| `ACTIVE` | `bitrix_active` | `false` → вход запрещён |
| — | `client_id`, `role`, `status` | задаёт **только владелец/админ клиента** |
| — | `last_login_at`, `profile_synced_at` | служебные |

- Поля, заданные у нас вручную (роль, статус), импортом не перезаписываются.
- Токены Битрикс24 после импорта храним только если нужны для синхронизации (refresh-токен — зашифрованно на сервере).

### 3.6. Роли (минимум для блока 1)

| Роль | Кто | Видит |
|---|---|---|
| `platform_owner` | Анатолий — **только в админке платформы** | все клиенты, подключение клиентов, добавление сотрудников |
| `client_admin` | Зуев (Матрёшка) | свою организацию целиком |
| `client_staff` + должность | Грузев «Закупщик» (сейчас), Анатолий (сейчас), другие — позже | своё по правам роли (детали — блок 2) |

- Два уровня ролей, хранятся раздельно в базе:
  - **уровень платформы** — флаг/роль `platform_owner` у пользователя; действует только в админке платформы;
  - **уровень клиента** — таблица членства (пользователь + `client_id` + роль `client_admin`/`client_staff`).
- Внутри клиента права считаются **только по членству** в этом клиенте; `platform_owner` в админке клиента не учитывается и не показывается.
- Переход между контурами — явный (переключатель «Платформа / Матрёшка»), текущий контекст хранится в сессии.
- Доступны серверу (`api/*`, RLS) в каждом запросе.
- Сейчас: Анатолий — `platform_owner` (платформа) + `client_staff` (Матрёшка); Грузев — `client_staff` «Закупщик» (Матрёшка). Роль `client_admin` заведена в модели, назначается позже (Зуев).

### 3.7. Сессии и выход
- Сессия бессрочная («помнить всегда»), переживает перезапуск браузера.
- «Выйти» — на этом устройстве; «Выйти на всех устройствах» — в профиле; владелец может разлогинить любого.
- Отзыв сессии при: выходе, отключении пользователя, `ACTIVE = false` при очередной проверке.

### 3.8. Критерии приёмки

**Сейчас (этап 1)**
1. На экране входа нет списка сотрудников; в JS-бандле нет email-ов и имён сотрудников.
2. Анатолий входит по email + пароль: в админке платформы видит всех клиентов (`platform_owner`); в админке Матрёшки он обычный пользователь (`client_staff`), без пометки и прав владельца платформы.
3. **Грузев входит по email + паролю (выданному Анатолием) в понедельник и видит админку Матрёшки как закупщик**; админка платформы ему недоступна.
4. 6-я неудачная попытка входа подряд → блок на 15 мин, запись в журнале; лимит по IP срабатывает.
5. Регистрация «с улицы» невозможна (ни через UI, ни прямым запросом к Supabase).
6. Сессия живёт неделю+ без повторного входа, переживает перезапуск браузера; «выйти на всех устройствах» её отзывает.
7. `api/*` знают роль и `client_id`; запрос без сессии → 401.
8. Провайдер `bitrix24` выключен: кнопки нет, `api/auth/bitrix/*` отвечает «не подключён»; в модели есть конфиг портала и поля профиля Битрикс24.
9. Публичные токен-страницы открываются без входа; секреты не встречаются в репозитории, логах и бандле.

**Позже (при подключении Битрикс24) — проверяются тогда**
10. Включение флага + заполнение конфига портала → кнопка «Войти через Битрикс24» работает без переделки кода входа.
11. Не добавленный владельцем сотрудник → «Доступ не выдан»; добавленный → профиль (ФИО, email, должность, отдел, фото, телефон) импортирован, роль не перезаписана.
12. Деактивированный в Битрикс24 или отключённый у нас — выкинут со всех устройств, `api/*` → 401.
13. Подменённый/просроченный `state` → отказ и запись в журнале; тестовые входы Зуева (`client_admin`) и Грузева (`client_staff`, «Закупщик»).

### 3.9. Как проверю вживую
- Превью Vercel из ветки → прогон критериев 1–9 → «да» Анатолия → мёрж в `oodobu` → ручной деплой через Vercel CLI.
- На проде: вход Анатолия и Грузева на `основа.redevelopment.pro` и `osnova.redevelopment.pro` (с телефона и компьютера); поиск email-ов/имён по собранному бандлу; `curl` к `api/*` без сессии → 401, к `api/auth/bitrix/*` → «не подключён»; прямой `signUp` через supabase-js → отказ; 6 неверных паролей на тестовом аккаунте → блок + запись в журнале; открытие токен-страниц в инкогнито.

## 4. Критика

### 4.1. Риски и противоречия
- **Срок vs объём.** К понедельнику реально нужен только вход + две учётки + отключение старых аккаунтов; лимиты, журнал и заготовка Битрикс24 могут не успеть. Предлагаю зафиксировать минимум к понедельнику (крит. 1–3, 5, 7, 9), остальное — следующим релизом.
- **«Отключён ≤ 1 мин» vs бессрочные сессии.** JWT Supabase живёт ~1 час; без серверной проверки статуса при каждом `api/*`-запросе (или короткого JWT) требование не выполняется. Нужна проверка `status` на сервере.
- **Блокировка по email = DoS.** 5 ошибок на email блокируют настоящего пользователя — любой, кто знает email Грузева, может его «запереть». Лучше: основной лимит по IP + задержки, блок по email — мягче.
- **Формулировка лимитов неоднозначна** (лимит «для `api/auth/*`» и «на `api/auth/bitrix/*`» в одной фразе) — уточнить, какой лимит на какой маршрут.
- **Саморегистрация:** закрывается только выключением signups в настройках Supabase Auth — это ручной шаг в Supabase, его легко забыть.
- **Два домена (`основа` / `osnova`).** Сессия Supabase хранится по origin: на одном домене вошёл — на другом нет. Redirect URL'ы Supabase и будущий redirect URI Битрикс24 должны учитывать оба (кириллический — в punycode `xn--80ad6adbq.redevelopment.pro`). Лучше выбрать один канонический домен, второй — редирект.
- **Крит. 6 «неделя+»** к понедельнику не проверить напрямую — проверяем перезапуском браузера и обновлением токена, неделю — постфактум.
